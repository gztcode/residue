## 1. 问题：同一个能力，三个词

| 出处 | 用词 | 实际指什么 |
|---|---|---|
| 决策 ② / §2 / A5 / AC-03 / AC-08 / AC-10 | 「自动删除」 | 用户显式启用后的**整体能力**（含开关、观察期、上限、逐项确认） |
| N3 / AC-19 / 第 ③ 页 | 「定时任务」 | 能力的**触发器**（何时启动一次执行） |
| P3 / V4 / AC-19 判定 | 「执行动作」 | 动作日志里的**单条原子动作**（`rename_to_trash`） |

三者不是三个功能，也不是三个状态类，而是**同一个能力在三个层次上的表述**。此前混用会造成两类风险：① 把「定时任务」误读成「无人值守、用户不可控」；② 把「执行动作」误读成「上游命令可以删」。CR-002 后执行体恒为产品，第二个风险已由 L1 定义堵住，但措辞层仍缺一张映射表。

## 2. 定名与可执行定义

| 层 | 定名 | 一句可执行定义 | 判定 / 承载编号 |
|---|---|---|---|
| **能力（范围层）** | **定时触发执行** | 用户显式启用后，由定时任务在触发点启动一次执行，按五要素合取把候选原子 rename 到废纸篓 | 决策 ②、§2、A5、AC-04 / AC-08 / AC-09 / V2 |
| **触发器** | **定时任务** | 默认每日 1 次、错峰、增量优先；用户可见可关；后台项须用户 consent | N3、AC-19 Given、N4、AC-10、§6 第 ③ 页 |
| **执行体** | **产品自身** | 恒为产品主进程 / 其派生只读 CLI 子进程；上游只做只读定位与举证、不产生删除动作 | AC-19、N5、AC-04、L1 定义 / CR-002-H |
| **执行动作** | **`rename_to_trash`** | 产品自身动作日志中记录的单条原子动作；`rm` / `unlink` / `unlinkat` / `rmdir` / `rename` 枚举调用出现次数为 0 | P3、V4「执行动作」、AC-19 判定 |

**定名理由**：选「定时触发执行」而非「自动删除」作为能力名，是因为它同时说清了「谁来触发（定时）」和「谁来干（执行）」，不含「无人值守」的暗示；但**决策 ② 原文「自动删除能力必须存在、用户可不启用」属八条锁定决策，逐字不动**——本卡统一的是 AC / N / P 层的解释口径，不改写用户拍过的范围表述。

## 3. 互斥关系

- 「自动删除」= 能力开关与范围表述（默认关、用户可不启用）；
- 「定时任务」= 触发器（配置对象，不是能力本身）；
- 「执行动作」= 日志字段值（单次可数、可举证）；
- 三者**不再互相指代**，也不对应三个状态类；§8 七类状态、P4 状态词表均不因此改动。

与既有概念的关系：T1 / T2 属判定维度，T3 / T4 属网络维度，U1–U4 属回退对象维度——本卡的「能力 / 触发器 / 执行体 / 执行动作」是**执行链维度**，与上述三组互不包含、不新增术语到 T / U 表。

## 4. 关键判定：AC-19 Given **不补**触发器类型

**判定：不补。** 理由三条：

1. AC-19 标题「定时任务的上游能力边界」与 Given「配置定时任务」已经封闭了触发器类型，再补「（触发器 = 定时触发）」是**同义重复**，不增加任何信息。
2. 补写会给 Given 引入一个新的可判定对象（「触发器类型」字段），而全文没有对应的状态词 / 字段 / 判定项承载它——这正是 CR-001 双 α 刚拆掉的「承诺与判定错配 / 无承载」类型。
3. 能力命名统一的目的在**解释口径**，定义性小节已足够；不动 AC 条文可保住 CR-003-H2（20 条 AC 主体与编号不动）与 H3。

**连带**：AC-19 的 When / Then / 判定项、N3、P3 全部逐字不改；「执行体恒为产品」已由 AC-19 Then「删除动作一律由产品按 N5 原子 rename」+ L1 定义 / CR-002-H 承载，无需重复写进 Given。
