## §0 事实核实（独立于交付总监观察，先于两张卡）

用户要求「独立验证，不要直接抄，也不要为了迎合而否定」，并点名核 `uv cache prune`。以下为核实结果；外部文档仅作事实来源，不构成本 PRD 编号。

| # | 核实对象 | 结论 | 对条文的直接后果 |
|---|---|---|---|
| F1 | `uv cache prune` | **纯本地内容寻址剪枝，不需要联网**。官方 CLI 定义为「Prune all unreachable objects from the cache」；判定依据是本机缓存索引 + 活跃 venv / lockfile 的引用关系（`Cache::prune` 引用检查），并对缓存目录取**独占锁**（另一 uv 进程持锁时最多等 5 min，`--force` 则退出）；CLI 提供 `--offline`（Disable network access）显式开关。依据：astral-sh/uv `docs/reference/cli.md`、`crates/uv-cache/src/lib.rs`、`crates/uv/src/commands/cache_prune.rs`。 | AC-19 / B-01 里把它归入「在线安全能力 / 需联网」**不成立**；但它**直接删文件、不进废纸篓**这一 B-01 核心冲突**仍成立**，且与网络无关。 |
| F2 | `npm cache clean --force` | **纯本地** `_cacache`（content-addressable）删除；`npm cache verify` 明确为 offline verification。依据 npm v11 `docs/cli/commands/npm-cache`。 | 同上，不属「需联网」类。 |
| F3 | `brew cleanup` | **cleanup 本身纯本地**（删 Cellar 旧版本 + `~/Library/Caches/Homebrew`，有 `--dry-run` / `--prune=days`）。联网的是 `brew install` / `brew upgrade` **前置的 auto-update `brew update`**（默认 24h 周期，`HOMEBREW_NO_AUTO_UPDATE` 控制）；cleanup 是 install 的**后置自动动作**（`HOMEBREW_NO_INSTALL_CLEANUP` 控制）。依据 docs.brew.sh/FAQ、`brew cleanup` man。 | 交付总监观察「`brew cleanup` 默认触发 update」**措辞不精确**：不是 cleanup 触发 update，是 install/upgrade 触发 auto-update，二者在同一命令链路里同框出现。现象方向成立，归因需修正（不迎合、也不否定）。 |
| F4 | 「两个维度混成一个词」 | **观察成立，且比原观察更严重**：AC-19 上游集合里 `uv cache prune` / `npm cache clean --force` / `brew cleanup` 三条 prune/clean 命令**全部纯本地**，没有任何一条「需要网络连通」；唯一网络动作是 brew auto-update，且不由产品发起、也不在 AC-19 集合内。故 §8「离线」的**触发物在现行条文里基本不存在**。 | §8「离线」不只「词义混淆的产物」，更是**无触发物的状态类**（设计 B3 第 1/3 条矛盾的根因）。 |
| F5 | 维度① 的准确归属 | 「服务运行中仍可执行」不等于「进程在线」：`uv cache prune` 的真实约束是它自己的**缓存独占锁**（F1）与 AC-05 / P-L0 的**活引用（fd / 文件锁 / cwd）判据**、N4 / §8「并发冲突」的批次边界——属**并发 / 活引用**维度，不是「在线」维度。 | 应归到既有 AC-05、P-L0、§8「并发冲突」，不新造「在线」状态词。 |

**对 B-01 的复评结论（CR-001 影响面表点名项）**：联网变量被排除 → B-01 选项①「上游只做只读探测」的可行性**不因「联网前提」而降低**；但选项①的代价（v2.0 L465「失去 `uv cache prune` 的可达性剪枝能力，产品须自研可达性判定，工程量与误判风险显著上升」）**依然成立**，其归因须从「在线安全 / 联网」改写为「本地引用图可达性判定须自行实现 + prune 本身是真删除（N5 / AC-13 / 核心功能 C3）不可用」。另：只读举证只能用 `uv cache dir` / `npm cache ls` / `brew --cache` 一类只读定位命令，正是 B-01 已指出的「集合不含只读定位命令」缺口。**B-01 选项①/② 本卡不代拍**；本条作为 CR-001 归档事实供复评取用。

### A.2 术语拆解（互斥 · 各自可判定 · 各一句定义）

| 术语 | 一句可执行定义 | 判定依据（挂编号） | 与其余术语的互斥点 |
|---|---|---|---|
| **T1 本地引用可达性（剪枝判定）** | 上游依据本机缓存索引与活跃 venv / lockfile 引用关系，判定并删除「不可达对象」的本地操作。 | 在 `--offline` 下执行前后目标缓存目录条目数减少，且 P1 窗口过滤后出站连接数 = 0（AC-01 / AC-12 / P1）。 | **能力**，不是状态，不进 §8 状态类；不涉及网络。 |
| **T2 并发 / 活引用可执行性** | 清理动作在目标进程仍存活或缓存独占锁被持有时能否执行。 | 按 P-L0「持有」判据（fd / 文件锁 / cwd 三者之一，AC-05）、AC-20 / N4 批次边界、§8「并发冲突」既有状态词判定；命中即 AC-05 阻断或 AC-20 顺延。 | 归既有 AC-05 / P-L0 / §8「并发冲突」，**不新造「在线」状态词**；不涉及网络。 |
| **T3 网络连通性** | 产品进程树或其派生的 CLI 子进程能否建立出站连接，以及上游命令是否附带网络动作（brew auto-update）。 | P1 观测窗口内过滤后出站连接数是否 > 0；`HOMEBREW_NO_AUTO_UPDATE` 是否生效（N6 / C-09 / AC-19）。 | 唯一的网络维度；「网络通不通」≠ A3 / N7 的「产品发不发」。 |
| **T4 零外发（产品承诺）** | 产品自身不主动发起任何外发，是 A3 / N7 / P1 已定义的约束。 | P1 窗口内过滤后出站连接数 = 0（AC-01 / AC-12 / P1）。 | **约束**，不是状态，也不是「在线 / 离线」的前提。 |

互斥关系：T1 / T2 / T4 均为本地或无网络维度，T3 为唯一网络维度；四者互不包含。「在线」「离线」「在线安全」「在线自证」四词**均不再作为需求术语使用**——是废止还是收窄，见 A.3 三方案与 A.4 拍板点。
