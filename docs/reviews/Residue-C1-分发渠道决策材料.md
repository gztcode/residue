## 1. 先纠正我此前的说法

我此前说「MAS 沙箱很可能砍掉自动删除能力」。**说轻了，也说偏了。**

被砍的不是一个「删除」按钮，而是产品赖以成立的**三件事**：

1. **全域发现**——产品的第一价值是「看到各环境占用」。而 `~/.cache/uv`、`~/.npm/_npx`、`~/.cache/pip` 是散落、隐式、会新增的路径，用户不可能预先全部圈出来。沙盒下 App 默认连**只读扫描**都做不到，除非用户手动选目录（F1/F3）。恰好「System Cache Files」在 F7 里就是被砍项。
2. **无人值守自动删除**——决策 ② 要求「自动删除必须存在、用户可不启用」。2.4.5(iii) 禁止退出后仍运行的进程（F2），后台项用户随时可关（F5），MacPaw 直接砍掉 Agent（F7）。
3. **L2 第 4 档常驻文件事件采样**——你此前拍板「四档全做、分层默认」。常驻采样进程在 MAS 下比定时任务更难成立。

换句话说：**MAS 不是削弱功能，是把产品的信息架构换掉了**——从「全域扫描 + 自动清理」变成「用户圈定范围 + 会话内手动清理」。

## 3. 两个反直觉点

**反直觉一：零外发承诺在两个渠道里的成本方向是相反的。**
MAS 把更新交给 Apple，产品自己一个包都不用发；官网分发要维持 2C 的安全更新与崩溃可见性，就必须自建通道，而一个「会删别人文件」的 App 恰恰最不能没有及时的安全更新。所以「零外发」不是官网分发的免费属性，而是要付代价去重新定义边界的。PRD 里目前只登记了「C1 若拍板引入更新通道，T3 被激活须重评本方案与 §7 第三方回调」，没写清这个方向。

**反直觉二：P1 的窗口定义已经帮我们挡掉了一次返工。**
P1 观测对象 = **产品主进程 + 其派生的 CLI 子进程**，窗口 = **触发动作前 1 s 至动作结束后 5 s**，过滤回环 / OCSP / NTP / mDNS。因此：
- 启动时的版本检查**不在清理动作窗口内**；
- Gatekeeper 首次启动校验公证 ticket 是**系统进程**行为，不是产品进程树（F6）；
- → 引入更新通道**不必然需要重写 AC-01 / AC-12 的判定项**。
需要改的是 **A3 假设条文的字面表述**（「零外发」→「清理链路零外发 + 明确的更新通道白名单」）与 **§7 第三方回调**登记，属于措辞与边界变更，不是 20 条 AC 主体变更。

**还有一个流程上的自我纠错**：我上一轮建议「PRD v3.0 可冻结」。但 C1 一旦拍板就会动 A3 与 §7，先冻结再开变更单是无谓往返。**建议把冻结推到 C1 拍完、A3/§7 一并改完之后**，这轮先不冻结。

## 4. 推导：这个开放项其实已经不开放了

把已锁定的东西叠起来看：

- 决策 ②：自动删除能力必须存在（用户可不启用，但要有）→ 排除「MAS 削功能」；
- 决策 ⑤ / ⑥：L2 四档全做、分层默认 → 排除「砍常驻采样」；
- 产品第一价值与各环境占用总览 → 排除「只能扫用户圈定的目录」；
- 受众 A1（个人开发者 / AI 重度用户）→ 这群人习惯 GitHub Release、Homebrew、签名与公证校验，本来就更信任官网分发，且会主动警惕「商店版功能残缺」；
- §6 已锁定 macOS 原生唯一形态、7 页 × 1 形态。

**结论（推导，不是拍板）：官网分发 + Developer ID 签名 + 公证 + stapled ticket，是唯一能保住已锁定范围的渠道。** 前面几轮决策已经把 C1 的自由度收掉了，它现在更像一道「确认题」，而不是一道「选择题」。

而且选 MAS 还有个隐性代价：F3 的「用户逐目录授权 + bookmark stale / 可撤销」在现有 PRD 里**没有任何 AC 或状态类承载**，§8 的 7 类状态也不含它。真选 MAS，刚收口的契约要重新开洞，等于把 CR-001 刚拆干净的概念又请回来。

## 5. 真正剩下要你拍的：更新 / 崩溃通道的边界

| 档 | 做法 | 代价 |
|---|---|---|
| **① 完全不自更新** | 只发布新版本，用户手动下载校验 | 零外发一字不改；但 2C 安全更新靠用户自觉，对会删文件的产品偏轻率 |
| **② 仅版本检查 + 跳转官网（我推荐）** | 一次纯文本版本清单请求，不后台下载、不上传任何本机信息，用户点「去下载」才跳浏览器；可关闭 | A3 措辞要改、§7 要登记这个唯一白名单；不出站用户数据，T4 的实质承诺保得住 |
| **③ 完整自动更新（Sparkle 类）** | 后台下载并静默替换 | 出站常态化；「零外发」必须重定义为「不主动外发用户数据」，安全举证成本显著上升 |

崩溃上报建议与②同档处理：**默认不做**；若要，只能做「本地留日志 + 用户主动导出提交」，也就是 PRD 里 A3 已经写过的那条边界，不新开自动上报。

## 6. 第三条路（如实登记，不推荐首版）

MacPaw 式**双版本**：MAS 上架「只读总览 + 手动清理」作为信任背书与获客入口，官网分发全功能版。

- 优点：Apple 背书 + 完整能力都拿到。
- 代价：两套构建 / 签名 / 公证 / 更新链路；同一产品两套功能矩阵，2C 用户极易困惑「为什么商店版没有自动删除」，信任反而受损；且会给 §6「7 页 × 1 形态」引入 AC 分支，触发交付面复核。对第一版偏重。
- 若将来要试，建议作为第二阶段的分发实验，不进本期。

## 9. 讨论中的概念澄清（2026-11-07 · 待落 CR 确认，不改动契约正文）

> 依交付流程登记：本节辨析由交付总监**按契约原文裁定**；**涉及范围与术语定义的改动归产品经理柯求真，本节不代改、不口头生效**。每条挂编号，挂不上编号的不成立。

### 9.1 术语补正：MAS 不是 Mac

| 词 | 指什么 |
|---|---|
| Mac | 机器 / 硬件平台 |
| macOS | 操作系统 |
| **Mac App Store（缩写 MAS）** | **分发渠道**，Apple 的 Mac 应用商店 |
| App Sandbox | 从 MAS 分发的 App 被强制启用的沙盒机制 |

本材料及前几轮的「MAS 沙箱」= 走 Mac App Store 渠道时强制生效的 App Sandbox，**不是「Mac 的沙箱」**。此前缩写首次出现未展开，在此补正；后续文档首次出现一律写全「Mac App Store（下称 MAS）」。

### 9.2 「定时删除」vs「定时启动脚本去删除」：同一件事，但这个拆分有用

**按契约原文裁定：OS 与审核视角不区分这两种描述。** 2.4.5(iii) 管的是「有没有未经同意的自启 / 退出 App 后仍运行的后台进程」，**不管进程里跑的是脚本还是原生代码**。定时唤醒一个执行删除的进程 = 注册 launchd / SMAppService 后台项，正是该条覆盖的对象。

- **consent 是唯一变量**：macOS 13+ `SMAppService` 后台项用户可见可关；macOS 26+ 退出 App 后仍活跃的后台任务还会弹窗追问一次。有 consent 的后台任务，技术上可注册。
- **实证口径修正**：MacPaw 砍掉 MAS 版 Updater / Agent（F7）不等于「Apple 明令禁止」，而是审核实践与风险偏好下的选择。准确说法是「**MAS 下这条路径不确定**」，不是「MAS 禁止」——这点我上一轮说绝对了。
- **真正卡住的从来不是「定时」，是「访问范围」**：脚本被唤醒后能碰哪些路径，由 Powerbox 显式选择 + security-scoped bookmark 决定（F3），硬编码 `~/.cache/uv` 不携带 sandbox extension。AI 工具缓存恰好散落、隐式、会新增。**定时可以谈 consent，全域发现谈不了** → 第 4 节推导不变，反而收得更紧。

**用户的拆分在契约层有用**：它把「触发器」与「执行体」分开。现有契约本来就是这么写的——**N3**「定时任务默认每日 1 次、错峰、增量优先」、**AC-19**「定时任务的上游能力边界」、**N4** 单次执行超时 ≤ 5 min、**AC-10** 可查标识；CR-002 后**执行体恒为产品自身**（N5 原子 rename），上游命令只做只读定位与举证。所以「定时启动脚本去删除」不是新方案，是 AC-19 已有形态的另一种说法。

**由此暴露一个需求层措辞歧义（登记，不代改）**：决策 ② / §2 / A5 用「自动删除」，AC-19 用「定时任务」，P3 用「执行动作」。是否把能力名统一为「定时触发执行」、并在 AC-19 Given 写明触发器类型，属**范围与术语定义，归柯求真出概念定义、走 CR，不口头改**。影子观察期、逐项确认、单次上限已由 AC-08 / AC-09 / V2 等处管住「无人值守」的边界，不因此新增机制。

### 9.3 「本地肯定要留档」：已在契约内，且比留档更强

- 已有承载：**V4** 举证链 8 个顶层字段（含「执行动作」「恢复位置」）、**P3** 产品自身执行动作日志（动作字段恒为 `rename_to_trash`、删除调用枚举出现次数 0）、**N7** 本机单一 jsonl + 一键清除、**AC-12** 随时清除、**AC-13** 恢复位置、**§6 第 ⑦ 页**举证链 / 执行日志（只读）、**S4** U2 文件恢复触发率。
- **CR-002 的隐藏理由**：把删除主体统一为产品、上游只做只读探测，正是为了**留档不断链**——若让 `uv cache prune` 直接删，产品拿不到逐条 rename 记录，V4 的「执行动作 / 恢复位置」就没有来源。这条要求与 CR-002 裁决同向，不是新增需求。
- **但它又给 C1 加了一条论据**：A3 已写「用户主动本机导出日志 + 自行提交属用户行为」，即留档须**用户可查可导出**。MAS 沙盒下日志写进 App 容器则用户不可见，且 2.4.5(i) 有真实拒审案例，Apple 原话「The app saves user data to the app's container, which is not user accessible」；写到用户可见位置又需额外授权。→ **「本地留档且用户可查」本身偏向官网分发**。
- 唯一还空着的格子：**P5 三件套里的留存期限 = C3**（未拍板前不自动删除日志），与 N7 一键清除、AC-12 随时清除配套。C3 仍待用户拍板。

### 10.3 追加事实基线 F8–F11（2026-11-07 核实）

| # | 事实 | 来源 |
|---|---|---|
| F8 | 站外下载的 App，macOS 默认检查 Developer ID 签名，Catalina 起**默认要求公证**；未公证会出现「Apple 无法检查是否含恶意软件 / 开发者无法验证」。macOS 15 Sequoia 起移除右键「打开」绕过，须到「系统设置 → 隐私与安全性 → 仍要打开」，且该入口约 1 小时内有效 | Apple《Open apps safely on your Mac》+ 2026 年实践资料 |

### 10.4 对契约的真实影响：比我上一轮说的更轻，但更细

**先纠正我上一轮的措辞**：我说「C1 一拍就会动 A3 / §7」。准确说法是——**GitHub 直发本身不产生任何产品运行时外发**，动不动条文取决于更新通道档位：

- `notarytool` 提交 = **发布侧 CI 行为**，不是产品进程；

- P1 观测对象只含「产品主进程 + 派生 CLI 子进程」、窗口为清理动作前 1 s 至后 5 s（PRD v3.0 第 60 行）→ 二者都不进 T3 / T4 判定。
