## 由 v1.2 改动新引入的问题（无则写「无」）

| # | 位置 | 由哪处改动引起 | 问题 | 修法 |
|---|---|---|---|---|
| 1 | §5.1「加载期校验三连」② | §5.1 段表改写：新增 `segCount u32` + `18 B × segCount` 段表并置于 payload 之前，但 ② 的等式仍是段表引入前的形态（"文件长 − 8"） | **② 恒不成立，每一份合规文件加载必判 `E-304`。** 按布局：文件长 = `12 + headerLen + 4 + 18·segCount + Σ段长 + 4`（CRC32 是 u32 = 4 B）。② 要求 `Σ段长 + 头部长 == 文件长 − 8`：① 若"头部长"取 `headerLen` 字面（= `headerJSON` 字节数），等式漏了 `segCount 4 B + 段表 18·segCount`；② 若"头部长"取"含段表的全部头部"，则 `12+H+4+18S` 比等式所需的 `12+H+18S` 多 4 B——**两种读法都恒差 4 B（把 CRC 当 8 B）**。算例：3 来源 × 3 kind = 9 段、`headerJSON` 800 B → 文件长 = `982 + Σ段长`，② 期望 `974 + Σ段长`。后果：`E-304` 按 §6 是"同 `E-302`，先备份、不自动重置"，于是**每次启动都进"状态文件损坏"提示**，用户唯一出路是"重置本地状态"二次确认 → `a` 归零 —— 这正是上轮阻塞 4/10 要堵的"第二次白送门禁"，且从"磁盘满一次"退化为"装完即触发" | 写死 `headerLen = headerJSON 字节数`；② 改为 `12 + headerLen + 4 + 18·segCount + Σ段长 + 4 == 文件长`（或保留减法式但写"文件长 − 4"并把"头部长"定义为 `16 + headerLen + 18·segCount`）；CRC 字段明确标注 `u32(4 B)` |
| 2 | §10.3「断电三态的判定」 | v1.2 新增 `state/migrating.json`（带 `step`）与三态判定规则（SRE 第 7 条处置） | **`step` 不足以判定，且判据用错了量。** ① **判据错**：`step ≥ 4` 分支写"先校验原件 CRC：完好则视为迁移未完成、删 `.bak` 重做"——但**迁移成功后原件 CRC 必然也完好**。具体断电点：④ 已 `rename` 新件入位（原件此时 = `toSchema`）→ ⑤ 删 `.bak` 与删 `migrating.json` 之间断电 → 重启判"未完成" → **对已是 `toSchema` 的原件再跑一次 `fromSchema → toSchema` 迁移**（按旧布局解析新件）→ 读出错位数据或 `E-304`，且此时唯一能救的 `.bak` 被删。② **`step` 更新时点全文未定义**（②只写一次，`{step, …}` 无二次写入规定）：实现 A 让 `step` 恒 < 4 → `step ≥ 4` 分支成死代码，无法应对"④ 中途原件损坏"；实现 B 在 ④ 的 `rename` 前把 `step` 更新为 4（分支存在的唯一理由）→ 正好触发 ① 的二次迁移。**两种合理实现分别产出"判不出"与"误判重做"**。③ `step < 4` 分支"直接删 `.bak`"前**不校验原件是否存在**：③ 的"写 `.bak`（原子）"未写死 copy 还是 move，若实现为 `rename(原件 → .bak)`，则 ④ 之前断电时原件不存在 → 仍执行"删 `.bak` + 正常加载原件" → 唯一数据与 `a` 全失。④ 两次 rename 各自原子（`migrating.json` 与 `.bak` 都"原子 + fsync"），但**没有任何一步持久记录"新件已就位"**，所以两次之间的窗口只能靠读原件 `schemaVersion` 闭合，`step` 闭合不了 | 判定改为读**原件可解析的 `schemaVersion`**：`== toSchema` → 迁移已完成（删 `.bak`、删 `migrating.json`，**不重做**）；`== fromSchema` → 未完成（先校验 `.bak` 可解析，再重做）；读不出 / CRC 失败 → 从 `.bak` 恢复，恢复后仍不可解析 → `E-306` 只读。并补三条：③ 写死为 copy + `rename`（禁 move 原件）；④ 的 `rename` 前把 `step` 原子更新为 4（含 `fsync` + `fsync(dir)`，写明这是 `step` 的唯一更新点）；删 `.bak` 前断言"原件存在 ∧ `schemaVersion == toSchema`" |

## 附注（非阻塞，补一句即可）

1. **§5.1 段头未写死定长/字节序/偏移基准**：按字段宽度可推出每条 `1+1+8+8 = 18 B`，`segCount × 18` 即段表长度——**段表的大小自描述是成立的**（回答本轮指定核对点 1）。但文档未写"定长 18 B、小端、无对齐填充"，若实现把 `(UInt8, UInt8, UInt64, UInt64)` 直接按 Swift struct 内存落盘则是 24 B/条（`UInt64` 8 字节对齐），读写步长不一致 → 段偏移整体错位。同理 `offset` 的基准（相对 payload 起始还是文件头）与 ① "不越界"的"界"（payload 区还是文件长）均未写死。同一实现内自洽，故不判阻塞。
2. **§2 落盘行（第 134 行）仍只列 `state.residue` + `records/*.jsonl`**，与 §5.5 的 `journal.jsonl` / `checkpoints.json` 登记不一致。第 7 条的实质已由 §5.5 + §10.3 闭合，此处仅文档同步。
