## 六问逐条回答

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| 1 | §10.1 六步发布准入，敢不敢签 | **不通过** | 六步只证明「构建产物签名链正确」，**零条**证明「装到干净机器上能跑、跑完能回滚」。缺端到端装机（#1）、缺 SHA-256 对账与旧版包留存（#2）、缺回滚演练（#4）。另注：§10.1-4「`stapler staple` 必须对 `.app` 做…staple 后再重新打 zip」是对的，但**没有一条要求「重新打的 zip/dmg 的哈希再验一次」** → 分发的可能是 staple 前的包 |
| 2 | 回滚路径（ADR-07 只读降级） | **不通过** | ① 只读 = **清理能力为 0**，且 ADR-07 同时封死「降级迁移」与「重置」两条出路 → 回滚后产品就是个只读查看器，**回滚后产品实际不可用**（核心功能不可用），且 §10.2 未声明这个代价；② 全篇**没有回滚演练的主体 / 时点 / 判据**；③「数据不丢、观察期进度保留」**不成立**：只读不写 → `a` 的载体确实不丢，但旧版「不认识新字段」，未识别量的默认值会把 `a` / `countedDays` **显示成 0**，用户看到的是「零误判、0/14 天」，实为「读不到」。详见阻塞 #3 / #4 / #5 |
| 3 | §5.5 journal + §5.3 `execution.jsonl` 能否答「删了什么 / 何时 / 谁触发 / 能否恢复」 | **不通过** | ① **能**：`candidatePath` + `bytes` + `bytesKind`（§5.3 已修「目录 `st_size` ≈ 96 B」的坑）；② **能**：`at` / journal `movedAt`；③ **不能**：两处都**没有 trigger 字段**，`jobId` 无命名规范，定时与手动**在落盘物上不可区分**；④ **部分不能**：`restorePath` + 运行时查废纸篓能答「现在能不能恢复」，但 U2 恢复后**不回写任何记录**（`action` 枚举无 `restored`），答不出「是否已经恢复过」→ 恢复列表会重复展示并可二次恢复。按本轮硬规则「有一条答不出即阻塞」→ **阻塞 2 条**（#6 / 建议 S1） |
| 4 | 零遥测下，用户报「删错了」能否靠脱敏报告定位根因 | **不通过** | **不能到根因，只能到「现场」**。能答：哪一条、哪一刻、哪条规则（`ruleHit`）、L0 两次检查的时点（`l0CheckAt`）、是否撞上限（AC-15 对账）。**答不出：为什么 L0 认为没有活引用** ——`P_now`（vnode→pid 倒排）与 `L0Snapshot.degraded` / `coverage` **全部只在内存、不落盘**（IF-03 只定义为返回值）→ 无法区分「L0 判错」与「L0 看不见」。而在 degraded 环境下误删，恰恰是最可能的根因。这比「没有遥测」更糟：**有日志但日志系统性地指向不了根因**。最小字段集见下 |
| 5 | 迁移失败爆炸半径 | **不通过** | ① 恢复本身失败（磁盘满）无任何出口：**没有错误码、没有指引、没有「保持可启动」的降级分支**，且每次启动都会重试迁移 → 永久不可用（#8）；② 断电后状态**在规范里没有定义**：无 `migrating` 标记，三种断电时刻三种残留形态，重启该重跑还是该认 `.bak` 为完成，实现自由发挥（#7）；③ **峰值 = 3.0 × 336 MB = 1008 MB**，§10.3 预检只要求 739–806 MB，**缺口 202–269 MB**（#6 算式见下） |
| 6 | 三类事故一线处置 | **通过** | 三类都能在 5 步内用手上已有的东西收场：A 走「退出 App → 第 ⑦ 页恢复 / Finder 废纸篓拖回」；B 走「看提示串 → 拷走 `state/` → 用 `.bak` 顶回」；C 走「`spctl` 分类 → `shasum` 对账」。**但**：A 的定位深度受 #6 / #10 限制（只能给到「疑似 L0 盲区」），B 的第一步受 #9 限制（E-302 会引导用户重置，而重置会清 `a`）|

### 问 5 ③ 的算式（自己算，与 §10.3 对账）

§10.3 原文：「需 `≥ 2 × 状态文件 + 20%`」。

| 时点 | 磁盘上同时存在 | 占用 |
|---|---|---|
| 迁移前 | `state.residue` | 336 MB |
| 造 `.bak`（原子 = 写 `.bak.tmp` → rename） | 原 + `.bak.tmp` | 672 MB |
| 迁移写新文件（写 `new.tmp`，§8.2 禁 truncate 目标） | 原 + `.bak` + `new.tmp` | **1008 MB** |
| rename 成功、删 `.bak` 前 | 新 + `.bak` | 672 MB |

| 预检读数 | 计算 | 结果 |
|---|---|---|
| 20% 作用于「2 × 状态文件」 | 672 × 1.2 | 806.4 MB |
| 20% 作用于「单份状态文件」 | 672 + 67.2 | 739.2 MB |
| **实际需要（峰值）** | 3 × 336 | **1008 MB** |
| **缺口** | 1008 − (739…806) | **202–269 MB** |

**结论：预检公式少了整整一份。**在「剩余空间恰好满足预检」的机器上，迁移会在**写 `new.tmp` 的最后 200 MB 处 ENOSPC**。而 §8.2 的 `E-303` 分支只是「删 tmp、不 rename」——旧数据确实保住了，但**用户永远迁不过去**，且 `.bak`（336 MB）在失败分支**不删**（§10.3 只在「成功后立即删」），等于把用户的可用空间再永久吃掉一份 → 越试越死。

### 问 4 的最小可定位字段集（只用既有落盘物，不新增采集）

| # | 来源 | 字段 | 现有 / 缺 |
|---|---|---|---|
| 1 | `state.residue` header | `schemaVersion` `appVersion` `round` `countedDays`；每来源 `T` `K` `J` `H` `a` `b` | 现有（IF-12 未定义导出是否包含 → 必须包含） |
| 2 | `scan.jsonl` | 误删前后各 2 行：`at` `mode` `filesScanned` `bytesScanned` `durationMs` `aborted` `unknownCount` | 现有 |
| 3 | `execution.jsonl` | 该 `jobId` 全行：`jobId` `candidateId` `seq` `at` `source` `candidatePath` `bytes` `bytesKind` `action` `trashPath` `restorePath` `appVersion` `round` | 现有；**缺 `trigger`** |
| 4 | `evidence.jsonl` | 8 字段全量，重点 `ruleHit.ruleId` `ruleHit.ruleVersion` `l0CheckAt.first` `l0CheckAt.second` `birthtime` | 现有 |
| 5 | L0 快照（**不落盘**） | `degraded`、`coverage.sameUIDTotal` `sameUIDRead` `statOtherUID`（只存计数，不存 pid） | **缺** |
| 6 | L0 规模（**不落盘**） | 本次快照的 fd 总数 / 命中数 / `excludePIDs` 是否生效（计数级） | **缺** |

**判定**：有 1–4 只能回答「它删了哪条、按哪条规则、L0 在哪个时刻检查过」；有 5–6 才能回答「这一次 L0 到底看不看得见」。**没有 5–6，「删错了」与「删对了但用户不知道那是他在用的文件」在同一份报告里长得一模一样** —— 这不是数据不足，是根因维度缺失。

## 三类事故的一线处置步骤

> 只用手上已有的东西：第 ⑦ 页执行日志 / 恢复入口、退出 App、系统设置 → 登录项、`~/Library/Application Support/Residue/state/`、`~/.Trash`、`shasum` / `spctl` / `codesign` / `xattr`、第 ⑦ 页导出脱敏报告、GitHub Issues。

### 事故 A：删了不该删的

1. **先停血**：菜单栏 → 退出 Residue（关窗只是驻留，**必须退出**）；再到「系统设置 → 通用 → 登录项」把 Residue 关掉，防止下次登录自动跑定时任务。
2. **别碰两样东西**：**不要点「一键清除」**（会删 `records/*.jsonl`，恢复依据当场消失）、**不要清空废纸篓**（`trashPath` 指向的就是废纸篓里的条目，清了等于放弃 14 日承诺）。
3. **恢复**：第 ⑦ 页执行日志按时间找到该条 → 点恢复（AC-13），文件回到 `restorePath`。App 起不来时走 Finder：打开废纸篓，按修改时间定位，拖回原目录（`execution.jsonl` 的 `candidatePath` 就是原路径）。
4. **断源**：第 ③ 页关掉自动删除开关，避免下一轮再删同一批。
5. **留证**：第 ⑦ 页导出脱敏报告 → 记下该条 `at`、路径末两段、`ruleId` → 提交 Issue。**如实告知用户**：本版本没有任何外发，我方无法远程复现，只能靠这份报告；报告里**不含** L0 当时的进程视图，因此大概率只能给到「疑似活引用判定盲区」，给不出确证（见阻塞 #10）。

### 事故 B：状态文件损坏 / 页面全是 0

1. **先分辨三种「全是 0」**：看提示串——「数据由更高版本创建，本版本只读」= `E-301`（**不是损坏**，是回滚态，见第 5 步）；「状态文件损坏」= `E-302`；段校验失败 = `E-304`。
2. **立刻退出 App**（防止调度器写入覆盖现场），**不要点任何「重置」**。`E-302` 的用户可见结果写着「需重置本地状态」，而 §10.2 明写「不引导重置」—— 这两句现在是打架的（阻塞 #9），**一线按 §10.2 执行：不重置**。
3. **整体留证**：把 `~/Library/Application Support/Residue/state/` **整个目录复制**（不是移动）到桌面。
4. **优先用 `.bak` 顶回**：若目录里有 `state.residue.bak`（迁移失败遗留），把它**复制**成 `state.residue`（保留 `.bak` 原件），重启。这是唯一「不丢 `a`」的恢复路径。
5. **顶不回来**：保留 `state.residue.corrupt`，导出脱敏报告 → 提 Issue，明确写「保持只读可启动、不要重置」的诉求。若已误点重置 → 只能如实告知：`a` 已归零，观察期从零重算 14 天，本轮**不能再宣称零误判**。

### 事故 C：装不上 / 被 Gatekeeper 拦

1. **先分类**（四个提示对应四条不同根因）：「已损坏，无法打开」→ 公证/票据；「无法验证开发者」→ 签名/证书；「Apple 无法检查是否恶意软件」→ 离线首次校验；「双击无反应或图标变灰」→ App Translocation（未拖入 `/Applications`）。
2. **取证**：`spctl -a -vvv -t exec /Applications/Residue.app`（看 `source=` 与 `origin=`）+ `codesign -dv --verbose=4 /Applications/Residue.app`（看 Authority 链）+ `xattr -l /Applications/Residue.app`（看 quarantine）。
3. **对账**：`shasum -a 256 <下载的 .dmg>` 与 Release 说明比对。**不一致 = 下载损坏或被替换 → 重下，绝不绕过**（这一步是零遥测下唯一能证明「用户装的是我们发的包」的手段）。
4. **一致但 `spctl` 判 rejected(no notarization)** → 是我们的漏 staple：**停发**、出修复包。**不对外提供 `xattr -dr com.apple.quarantine` 之类的绕过指引** —— 那是教会用户绕过所有 Gatekeeper，代价远大于一次发布事故。
5. **不是装不上而是不跑**：`SMAppService.status == .requiresApproval` → 按 ADR-02 四态文案指引用户去「系统设置 → 通用 → 登录项」允许；`.notFound` → 属注册丢失，需重装（这一类**只能回「重装」**，我直说）。

## 阻塞项

| # | 位置 | 原文片段 | 什么情况下会炸 | 修法 |
|---|---|---|---|---|
| 1 | §10.1 | 「`codesign --verify --deep --strict` + `spctl --assess` 双验」 | 六步全绿、用户装上去首启就崩（未授权来源目录 / 登录项未批 / 从 `.dmg` 直接运行）。**炸在哪**：第一次使用即失败，而发布责任人此前没有任何一次「装上去跑通」的记录，事故第一小时只能靠猜。收场：只能紧急重发，但**旧版包又没留存**（见 #2）→ 无退路 | §10.1 增第 7 步「干净机端到端装机」（C-1）；判据：首启不崩 + 首扫落盘 + 登录项 `.enabled` + Translocation 提示出现 |
| 2 | §10.1 / N8 | 「产物：`.dmg`（内含 `.app`）或 `.zip`」 | ① 交付物清单缺 SHA-256 的**产出步骤**（PRD §6 第 2 项明确要求 `shasum -a 256` 校验值），发布后没人算哈希 → 用户与支持都无法确认装的是哪一版；② 全篇无「上一版安装包必须留存」→ §10.2 的「回滚 = 用户装回旧版」在 Release 上**没有旧版可装**。收场：事故时只能让用户等修复包 | §10.1 增「上传后重新下载比对哈希」（C-10）+「Release 保留 ≥ 上一版与哈希」（C-12）；三是把「构建 commit + 哈希 + notary submission id」写进 Release 说明 |
| 3 | §10.2 / ADR-07 | 「回滚 = 用户装回旧版」「**不提供降级迁移**；**不引导「重置本地状态」**」 | 新版因迁移 bug 而坏 → 用户回滚到旧版 → 只读 → **不能执行任何清理**（核心功能 0）；想恢复能力只有两条路，而两条都被自己封死：装回有 bug 的新版（等于没回滚）、重置（清掉 `a`，安全凭证没了）。**回滚路径只在「新版 UI/性能坏、数据格式没变」时成立**，而那时根本不需要只读降级。收场：产品变砖（能看不能用），一线无话可说 | §10.2 补两段：① 明写「回滚仅保证数据不被破坏、不被误写；**不恢复清理能力**；恢复能力唯一路径 = 安装修复版」；② 把该句同步进 Release 说明与 README（C-15）。不改机制、不加功能，只把能力边界说清 |
| 4 | §10.2 | 「旧版遇更高 `schemaVersion` → 只读模式」（无演练条款） | 只读分支**从未被执行过**。真回滚那天才发现旧版读到新文件直接抛 `E-304` → 落到「先备份 `.corrupt` 再报 `E-302`」→ 而 `E-302` 的可见结果写着「需重置」→ 用户一重置，`a` 清零，回滚把唯一安全凭证弄丢。收场：不可逆 | §10.2 增「回滚演练」条款：**谁** = 发布责任人；**何时** = 每次发布前，与发版同一次；**判据** = C-8 四项（提示串 / mtime+inode 不变 / 零新增行 / 无重置引导） |
| 5 | §10.2 / IF-09 | 「以只读模式加载**可识别字段**」 | 「可识别字段」没有契约。若新版把 `a` 从 header 挪进段、或新增 `kind`，旧读方要么断言失败（→ `E-304` → 见 #4），要么按缺省 0 读 → 界面显示「误判 0 · 检查 0 · 0/14 天」。**这是把「错 1 次永久」显示成「一次都没错」** —— 比不能读更危险。另：只读态的运行时边界也没定义（定时任务还跑不跑、`scan.jsonl` 还写不写、「确认清理」按钮是否禁用），按 §10.2「不写」字面，扫描器连 `scan.jsonl` 都不能写，但 ADR-02 的登录项仍在 | IF-09 增前向兼容契约三条：① 读方**必须**按 `(sourceIndex, kind)` 遍历段表并**跳过未知 `kind`**，**不得**断言 `segCount` 精确值；② header JSON 只增不改，未知键忽略；③ **未识别量一律显示「不适用 / 不可读」，禁止以 0 代缺**。并定义只读态运行时：调度停、所有落盘物零写、清理动作禁用并给原因串 |
| 6 | §10.3 | 「需 `≥ 2 × 状态文件 + 20%`」 | 预检低估整整一份（见上表算式）：336 MB 需 1008 MB，预检只放行 739–806 MB。**在「刚够预检」的机器上，迁移会在写 `new.tmp` 的最后 200 MB 处 ENOSPC** → `E-303` → 删 tmp、不 rename → 旧数据在，但**永远迁不过去**，且 `.bak`（336 MB）不删 → 用户空间被永久再吃一份，越试越死 | 公式改为绝对量：`可用空间 ≥ 3 × 状态文件 + 32 MB`（32 MB 留给 `records` 追加与 rename 元数据），并在 `E-305` 文案里给出「还差 N MB」。同步在 C-5 用实测峰值回填 |
| 7 | §10.3 / §8.1 | 「④ **成功后立即删 `.bak`**」（状态机仅 `idle→scanning→judging→executing→restoring→idle`） | **无 `migrating` 标记、状态机无该态**。断电三种形态三种残留：① 造 `.bak` 中断 → `.bak.tmp` 垃圾；② 写 `new.tmp` 中断 → 原 + `.bak` + 半截 `new.tmp`；③ rename 后未删 `.bak` → 新格式 + 旧 `.bak`。重启时**三种都长得差不多**，该「重跑迁移」还是该「认 `.bak` 已完备」规范没说 → 实现若写成「`.bak` 存在即视为已完成 → 删 `.bak`」，就把唯一备份删了。收场：一次断电 = 一份 336 MB 的不可解释残留 + 一次赌博 | 迁移前三连：写 `state/migrating.json`（记 `fromSchema` `toSchema` `startedAt` `bakPath`，原子 + fsync）→ 迁移 → 删标记 → 删 `.bak`。启动时**先读标记**决定走「续做 / 回退 / 清理残留」，并给三种残留各一条确定分支。`migrating.json` 与 `*.tmp` 登记进 `state/` 运行期态 |
| 8 | §10.3 / §6 | 「失败 → 从 `.bak` 原子恢复 + `E-302`」 | **恢复本身失败（磁盘满 / 权限变）无出口**：恢复要写 336 MB 的 tmp，而这正是刚失败的原因 → 恢复再失败；没有任何错误码描述这个状态，没有指引，没有「至少让我以只读启动」的降级分支，而**每次启动都会重试迁移** → 用户面对的是一个反复启动失败、没有报错含义的 App。收场：只能靠用户自己去翻 `Application Support`（他不可能知道） | 增一条错误码（如 `E-306` 迁移回退失败），可见结果 = 「状态未更新，数据仍在 `state/`，请先释放 N MB 后重启」；并规定**此态必须以只读方式启动成功**（复用 ADR-07 只读渲染），不得每次启动重试写盘 |
| 9 | §6 / ADR-07 | `E-302` 用户可见结果：「需重置本地状态」 | 与 §10.2「**不引导「重置本地状态」**（重置会清掉 `a`）」**逐字相反**。CRC 失败（大概率是 bug 或断电）→ 界面让用户重置 → `a` 清零 → 「错 1 次永久」被一次损坏事件洗白。这不是文案问题，是**安全凭证被建议销毁** | `E-302` 可见结果改为「状态文件损坏，已备份；请导出诊断并联系支持，**不要重置**」，重置只作为「用户显式确认 + 二次确认 + 明示会清空观察期与误判记录」的隐藏动作；`E-304` 同 |
| 10 | §9 / IF-12 / ADR-08 | 「替换 `<user>` / `<path>` / `<host>`」（只定义脱敏，未定义报告含什么） | ① **导出报告的字段清单从未定义** —— 而 N8 第 4 项把「导出脱敏报告 + GitHub Issues」定为唯一反馈通道，通道里装什么是空的；② `degraded` / `coverage` / `P_now` 规模**全部只在内存**（IF-03 只作返回值）→ 用户报「删错了」时，一线只能给到「哪条、哪规则、哪时点」，**给不出「L0 当时看不看得见」**。收场的现实是：每一条误删申诉都以「无法复现、疑似环境差异」结案，而 `a` 照样 +1（或没 +1） | IF-12 增「报告内容清单」= 问 4 的最小集 1–4；并把 `L0Snapshot` 的 `degraded` + `coverage` 三计数**落到 `scan.jsonl` 一行**（计数级、无 pid、无路径，不构成新采集，仍是本机审计日志）→ 补齐最小集 5–6 |

## 建议项

| # | 位置 | 建议 | 是否超范围 |
|---|---|---|---|
| S1 | §5.3 | U2 手动恢复成功后**回写一条记录**（`action: "restored"` 或独立行，带 `restoredAt` + `via: user`）。现状：`action` 枚举里没有「已恢复」，`journal.restored` 只服务崩溃回退 → 第 ⑦ 页恢复列表会一直把已恢复的条目当成「还能恢复」，用户点第二次收 `E-201/E-205`，且支持侧无法回答「这条到底恢复没恢复」 | 否（补既有审计日志的一个枚举值，非新采集、非新文件） |
| S2 | §10.3 / S-10 | 「一键清除」范围补 `state/journal.jsonl`、`state/checkpoints.json`、`state/*.tmp`、`state/migrating.json`。现状清除范围 = `records/*.jsonl` + `*.bak` + `*.corrupt`，而 `journal.jsonl` 里有 `origPath` / `trashPath`、`checkpoints.json` 里有 `lastNameCompleted`（**都是路径**）→ 用户点了「清除全部采集与日志」，磁盘上仍留着他的路径；迁移失败还会留多份 `.tmp` 副本 | 否（把已有落盘物登记进既有清除范围，不加动作、不加页面） |

## 一句话

**我不敢签。** 这版把「包是干净的」证明得很扎实，把「装上能用、坏了能退、退了能交代、删了能复原」证明得一条都没有 —— 六步公证链再漂亮，也挡不住第一次安装就崩、迁移差 200 MB 就死、回滚之后只剩一个只能看的壳。
