## 二、交底三问的答复

### 2.1 A-4 一致性校验

**答：不能保证。R2 §5.5 的水位方案在真实 APFS 上不成立。**

R2 §5.5 规格是「父目录 inode + 已完成子项**名字典序最大值**作水位，恢复时同目录 `readdir` 跳过 `≤` 水位的名字」。实测（`/tmp/residue-probe/order.c`、`resume2.c`）：

1. **APFS `readdir` 返回顺序不是字典序**——实测目录 `readdir` 前 10 项为
   `cand_0014 cand_0043 cand_0106 cand_0055 cand_0110 other_0075 other_0061 other_0049 cand_0002 cand_0096`，
   完全是哈希序。**「字典序最大值」与「readdir 遍历位置」是两个不相干的量**。

2. **同目录内连续 5 次 `readdir` 顺序稳定**（无修改时），但**一旦目录有增删，顺序立即变化**：
   - 新增 5 个文件 → 原 300 条的相对顺序全部错位（实测位置 15 起逐条偏移）；
   - 删除 5 个文件 → 相对初始快照错位 274 处；
   - 再新增 200 个 → 错位 456 处。

3. **决定性实验**（`resume2.c`：200 项目录、120 候选、处理完前 60 项后中断）：
   - 基线（未中断全量）：文件数 120 / 字节数 7680；
   - **按 R2 §5.5 字面规格续扫**：合并后文件数 **36**、字节数 **2304**，
     三项一致性 **文件数 ✗ / 字节数 ✗ / 候选清单 ✗**——**漏掉 84 个候选（70%）**。
     根因：字典序水位落在 `other_0077.txt`，而绝大多数 `cand_*.cand` 的字典序**小于**它
     （`'c' < 'o'`）→ 恢复时被整批跳过。

**缺口（三个，逐条）**：

| 缺口 | 说明 | 我的处置（不改 R2 契约，只改实现细节） |
|---|---|---|
| **G-1 水位语义错误** | 「名字典序最大值」在非字典序的 `readdir` 下无意义 | 断点水位改为**「已完成子项名字集合」**（断点文件里存已处理名字的集合/摘要），恢复时按集合精确跳过。实测此法三项一致 **全部 ✓**。断点体积：`checkpoints.json` 存全量名字会大（328 万条目量级下不可接受）→ 用**分目录的滚动集合 + 每 2000 条或 2 s 落一次**，每目录只存该目录已处理名字的集合。 |
| **G-2 无「按名跳过」的原子能力** | POSIX 目录流只能顺序读，`readdir` 无 seek-by-name；`getdirentries64` 在 arm64 无符号（**实测确认**：`clang` 报 `call to undeclared function 'getdirentries64'`，与 R2 ADR-04 B6 一致） | 恢复时**仍要全量 `readdir` 该目录**，只是按名字集合跳过「已处理」的条目、不重复做 `getattrlistbulk`/候选判定。**这意味着「精确续扫」的收益在 I/O 而不在遍历**——这一点必须在 §5.5 的口径里说清，否则验收会误以为「续扫 = 不重读目录」。 |
| **G-3 一致性校验无自证载体** | 「三项一致」是**跨两次运行**的比较，需要一个可判定的载体 | 断点文件里必须落**扫描侧的三项摘要**（`filesScanned` / `bytesScanned` / 候选清单的稳定摘要，如候选路径集合的 SHA-256 或按路径排序后的滚动哈希）。续扫结束**重算三项并与断点里的摘要比对**；不一致 → `E-106` 要求全量重扫。**没有这个摘要，三项一致无法被机器判定，只能靠人看**。 |

**结论**：三项一致**可以做到**，但前提是把 §5.5 的「字典序水位」换成「已完成名字集合 + 三项摘要自证」。这属于**实现层修正**（不改 IF-01/IF-02 的契约签名与验收口径），我认领在 A-4 里，但需要交底方确认这不构成「改 R2」——这是异议 #1 的另一半。

### 2.2 A-7 序列化方式（明确选一个 + 代价）

**明确选：混合方案——`headerJSON` 用 `Codable`/`JSONEncoder`，段表（24 B/项）+ payload 用 `Data` 手写序列化。**

**为什么 `Codable` 排不出要求的布局（实测证据，`/tmp/residue-probe/serde.swift`）**：

- 9 个段表项经 `JSONEncoder` 编码后 = **746 B 的 JSON 数组**，不是 9 × 24 = 216 B 的定长二进制；
- `Codable` **没有「定长二进制记录」的表达能力**——`encode` 的产物长度必然随内容变化，
  而 §5.1 校验① 的尺寸恒等式 `… + 24×segCount + …` 要求段表长度**只由 `segCount` 决定**；
- JSON 文本格式的字节由 Foundation 决定（本产品不是格式的制定者），跨 macOS 版本不保证字节可复现
  ——这对「CRC32 + 迁移 + 回滚」是实打实的风险。

**混合方案的实测验证**（同一次运行）：

```
段表起点 = 61
payload 起点 = 277   （= 段表末尾，紧随其后）✓
尺寸恒等式: 4+4+4+45+4+24×9+1000+4 = 1281   (实测总长 1281) ✓
段0 反读: offset=0 length=100 kind=1 sourceIndex=0   (字段序 = §5.1 校验①) ✓
```

**代价（明说）**：

| 方案 | 优点 | 代价 |
|---|---|---|
| **全 Codable**（header + 段表 + payload） | 全自动，字段改名有编译器兜底 | **不可行**：排不出「段表紧跟 header、payload 紧随其后」的定长布局，尺寸恒等式无法成立，CRC 覆盖范围不可控 → **直接否** |
| **全手写 `Data`** | 字节完全自控 | `headerJSON` 里 `sources` 数组、`T/H/K/J` 可空、`note` 文本都要手写键值与转义 → **可维护性差、易漏字段**，且 §5.1 明确要求 header「可读，供审计」 |
| **混合（我选）** | header 用 `Codable` 保住可读性与类型安全；段表/payload 手写保住定长布局 | **需要写并维护两套序列化**：① 段表/payload 的手写编码器与解码器（约 300 行）；② **同一份字段在 header（`Codable`）与段表（手写）里各出现一次** → 正是 R2 §19 自己总结的「同一事实写在两处」那个复发模式，必须用机器断言两处一致（如：加载期断言 `slotCount` 与 `F` 段长、`sources.count` 与 `segCount/3` 一致） |

**明确回答交底单里的那句**：「如果你用 `Codable`，它排不出……这一条要改成手写」——**我不用 `Codable` 排段表**。段表与 payload 手写；`headerJSON` 这一块**保留 `Codable`**，因为它本来就是可读 JSON，不是定长二进制段。

**额外一句**：现有 `StateStore.swift` 是**全 JSON**（`state.json` + `JSONEncoder`），与 §5.1 的 `state.residue` 二进制格式**不是同一个载体**。A-7 是**新写一个载体**还是**改造现有的**？——这直接影响工时归属（§四 异议 #2）。

### 2.3 A-9 视图组织

**建议：7 个独立 View 文件，但共享一个「语义位渲染层」。**

理由（按重要性）：

1. **一个文件塞 7 个视图是这个规模下 SwiftUI 的明确反模式**。第 ⑤ 页要 `Table` + 固定列宽、第 ② 页要分页数据源（IF-06，`limit ≤ 200`）、第 ④ 页要错误码分支（`E-101`…`E-501` 十几种）、第 ⑦ 页要恢复列表 + 空态说明。7 页堆一个文件 ≈ 1500+ 行，任何一页改动都要在同一个文件的上下文里推理，冲突概率随页数线性上升。

2. **但「7 个独立文件」不等于「7 套各写各的」**——那正好会踩 R2 §3「L4 禁止任何算术」和 §12.2 的坑。所以我建议的结构是：

   ```
   Sources/ResidueUI/
   ├── AppShell.swift            // 7 页导航 + 菜单栏常驻（ADR-02）
   ├── Views/
   │   ├── Page1Status.swift
   │   ├── Page2Candidates.swift // Table + 分页数据源
   │   ├── Page3Schedule.swift
   │   ├── Page4Errors.swift     // 错误码 → 文案映射
   │   ├── Page5Report.swift
   │   ├── Page6Gate.swift       // a/b 显示
   │   └── Page7Restore.swift
   └── Semantics/
       ├── SemanticSlot.swift    // 语义位枚举（唯一取值处）
       └── SemanticText.swift    // 语义位 → 文本/状态的唯一渲染出口
   ```

   **`SemanticSlot` + `SemanticText` 是这次拆分的真正要点**：它把「界面能显示什么」收敛成一个枚举，7 个页面只能从枚举里取，不能自己拼字符串、不能自己算。R2 §12.2 说「三处必须调用同一个 `Metrics.l0Display(a:b:)`」——**那就不该让三处各自写**，应该让三处都渲染同一个 `SemanticSlot`。这样「L4 禁止算术」从「靠纪律」变成「靠类型」。

3. **代价（如实登记）**：比单文件多 8 个文件、约 +0.2 人日的文件骨架开销。但它换来的是**第 ① 页加一个语义位不用翻 1500 行**——而第 ① 页（状态条 + 登录项四态 + Translocation 提示 + 并发冲突）按 R2 §2 的映射表是**变动最频繁**的一页。

4. **与 §3.1 的关系**：我推荐 7 个独立文件，但**每个文件内部只放「语义位占位」**——即每页的结构、导航、状态位、错误码分支都到位，**具体的视觉呈现（间距、字号、颜色、文案措辞）留到 R1.5 之后统一刷**。所以拆文件不增加本阶段工时。

=== 端到端 L0Probe（含 vnode 倒排）===
同uid进程=624 fd=8587 vnode成功=7100  总耗时=8.0 ms

degraded(同uid失败)=false | statOtherUID=2699 | visibleFds=8584 | sameUIDTotal=624 | sameUIDRead=624

**多次运行的稳定性**（4 次）：

| 量 | 观测值 | 波动来源 |
|---|---|---|
| 进程表总条数 | 3,324 ～ 3,648 | 机器上并发进程数 |
| 同 uid 进程数 | 613 ～ 650 | 同上 |
| **同 uid 可读进程数** | **613～650 / 613～650 → 100%** | **恒为 100%，`EPERM` 恒为 0** |
| 可见 fd 总数 | 8,530 ～ 8,584 | 进程自身 fd 数 |
| 平均 fd/进程 | 13.8 ～ 13.9 | 同上 |
| 单进程最大 fd 数 | 319 | 同上 |
| vnode 提取成功率 | **99.2% ～ 99.3%**（仅 VNODE 型） | 少量 fd 在提取瞬间已关闭 |
| **端到端 L0Probe 耗时** | **6.9 ～ 11.6 ms** | 同上 |

> **关键不变式**：无论机器负载如何变化，**同 uid 进程可读率恒为 100%，`EPERM` 恒为 0**。这是 A-6 成立的根本依据。

**回答交底单的问题**：

| 问题 | 实测答案 |
|---|---|
| 本机能读到多少同 uid 进程的 fd？ | **全部同 uid 进程（613～650 个，可读率 100%），fd 总数 8,530～8,584（平均 13.8～13.9/进程，单进程最多 319）**。`EPERM = 0`。 |
| `proc_pidinfo(PROC_PIDLISTFDS)` 对同 uid 进程是否需要任何权限？ | **不需要**。零额外权限、零 TCC 弹窗。进程表里 2,699～2,997 个进程返回 `PROC_PIDTBSDINFO` 的 `EPERM`——那是**跨 uid 进程**，与同 uid 无关。 |
| 同 uid 能否读到 fd 的 **vnode 身份**？ | **能**。`PROC_PIDFDVNODEPATHINFO` 在 VNODE 型 fd 上成功率 **99.2%～99.3%**。 |
| `cwd` 能读到吗？ | **能**，`PROC_PIDVNODEPATHINFO` 624/624 成功（0.9 µs/进程）。 |
| `degraded` 会误置 true 吗？ | **不会**。同 uid 失败数 = 0 → `degraded = false`；跨 uid 的 2,699 个计入 `coverage.statOtherUID`。**R2 ADR-03 的定义正确，实测支持。** |
| 性能（R2 §7.2 的 L0 预算 1.5 s）？ | 实测端到端 **7～12 ms**，**比预算快约 100 倍**。R2 §7.2 假设「600 进程 × 120 fd = 7.2 万 fd」，实测是「~630 进程 × ~14 fd = ~8.5 千 fd」——**R2 的 fd 规模假设高估了约 8.5 倍**，但因为单价也高估了 100 倍，两边相消，L0 这项**不是风险项，是余量项**。 |

**决定性验证（不只是「能不能读到」，而是「能不能真的判定持有」）**（`/tmp/residue-probe/l0detect.c`）：

```
=== 目标文件 /tmp/residue-probe/hold/target.bin  dev=16777233 ino=28134464 ===
本进程持有它的 fd = 5
  [A] 命中 pid=96384 fd=5 path=/private/tmp/residue-probe/hold/target.bin
方案A（元素=proc_fdinfo 8B，fd=proc_fd字段）: 尝试 fd 关系=69856  命中目标=1
方案B（元素=proc_fileinfo 24B，fd=数组下标）: 尝试 fd 关系=69856  命中目标=1
```

→ 同 uid 进程持有的文件，**能被精确命中到 (dev, ino)**。**A-6 方案不需要改。**

**但有三个实现坑必须写进 A-6 的实现说明（都是我在实测中踩到的）**：

1. **`PROC_PIDLISTFDS` 的返回值是「字节数」，不是「元素个数」**。SDK 头文件写的是 `PROC_PIDLISTFD_SIZE = sizeof(struct proc_fdinfo)`（8 B），
   但内核实际按 **24 B/项**（`struct proc_fileinfo`）填充缓冲区。
   实测证据（`/tmp/residue-probe/fdsize.c`，本进程开 200 个 fd 并关掉中间一个制造空洞）：

   ```
   [8B元素] 返回值 got=1648   → 1648/8 = 206 项（错）
   [24B元素] 返回值 got=1648   → 1648/24 = 68 项（对：本进程实际约 68 个 fd）
   ```
   **按 8 B 元素解析会把 3 倍的脏数据当 fd 用**。按 24 B 解析时，fd 号 = **数组下标**（不是结构体里的字段）。
   → **实现必须用 `struct proc_fileinfo`（24 B）布局，fd 号取数组下标**。这是 R2 §15 B2 没有覆盖的一个坑。

2. **vnode 身份在 macOS 上没有独立 `vnodeid` 字段**。ADR-03 写「取 `vnodeid`」——实测 SDK 头文件里
   `struct vnode_info` 只有 `vi_stat / vi_type / vi_fsid`，**没有 `vnodeid`**。
   → 可用身份是 **(dev, ino) 二元组**（`vst_dev` + `vst_ino`），本产品自己拼成 `UInt64` 键（如 `dev << 32 | ino` 的等价编码）建倒排。
   **口径上必须统一**：报告与举证链里不能写「vnodeid」，应写「文件身份（设备号 + inode）」。

3. **只有 VNODE 型 fd 能进倒排**（实测占 83.9%）。socket / pipe / kqueue / netpolicy 型 fd 取不到 vnode，
   但它们**本来也不指向候选文件**，不影响判定。→ 倒排表只收 VNODE 型，其余计数但不查。

**FDH 现状**（顺带核实 ADR-06 的能力探测口径）：

```
不可读: /Users/<user>/Library/Safari
不可读: /Users/<user>/Library/Mail
不可读: /Users/<user>/Library/Messages
不可读: /Users/<user>/Library/Application Support/com.apple.TCC
~/.cache 可读（不在 TCC 保护范围）
```

→ 本机**没有 FDA**（TCC 保护目录全不可读），但 `~/.cache` 可读、L0 判定完全正常。
**这直接实测支持 R2 ADR-06 的改写**：「FDA 从前置授权降为失败后指引」是**正确的**，实测无需 FDA 也能干活。

### 3.3 A-4 扫描性能【实测数字】

**实测命令**（`/tmp/residue-probe/bulkperf.c`、`cold.c`，`clang -O2` 编译）：

```
$ clang -O2 -o /tmp/residue-probe/bulkperf /tmp/residue-probe/bulkperf.c && /tmp/residue-probe/bulkperf
$ clang -O2 -o /tmp/residue-probe/cold   /tmp/residue-probe/cold.c   && /tmp/residue-probe/cold
```

#### (a) `readdir` 速率

| 目录 | 条目数 | 冷 | 热 |
|---|---|---|---|
| `~/.cache`（真实现有目录） | 93,783（目录 8,819 / 文件 83,335 / symlink 1,629） | 139～485 ms → **193～674 k 条/s**（首次跑 485～569 ms → 165～193 k） | 129～136 ms → **689～727 k 条/s** |
| `~/Library/Caches` | 115,132 | 151 ms → **761 k 条/s** | 126 ms → **911 k 条/s** |
| 单目录 `~/.cache/magpie/calls-v15` | 1,601 | 0.6 ms → 2.57 M 条/s | 0.5 ms → 3.53 M 条/s |
| **真冷**新建树（1,000 目录 × 200 文件 = 201,000 项，刚写入、缓存未预热） | 201,000 | 60.4 ms → **3.33 M 条/s** | 55.8 ms → 3.60 M 条/s |

> 「冷」= 该目录本次首次遍历（此前未在缓存中）；实测冷热比约 **1.1～3.6×**，波动主要来自目录元数据在 APFS 上的落盘时机。
> 关键量级结论稳定：**冷缓存下 `readdir` 是 20 万～76 万条/s 量级，不是 3 万条/s 量级**。

**`DT_UNKNOWN` 实测 = 0**（全部 93,783 / 115,132 / 201,000 条目中一次都没出现）→ R2 ADR-04 的「APFS 极少 / M_unknown ≈ 1%」在 APFS 上是**过度保守**的，`lstat` 退路基本不会被触发。**验收口径③（`DT_UNKNOWN` 退回 `lstat` 并计数）需要构造才能测到**，建议质量组在用例里显式造一个 `DT_UNKNOWN`（或用非 APFS 卷 / 特殊挂载点），否则这条用例恒不触发、等于没测。

#### (b) `getattrlistbulk` 单条耗时

按 **man 2 getattrlistbulk** 的权威布局实现（`[u32 length][attribute_set_t returned][可选 u32 error][可选 attrreference_t name_info][payload]`，下一条 = 当前指针 + `length`）：

| 目录 | 条目数 | 256 KB 缓冲 | 64 KB 缓冲 |
|---|---|---|---|
| `~/.cache/magpie/calls-v15` | 1,601 | 0.628 ms → **0.392 µs/条** | 0.640 ms → 0.400 µs/条 |
| `~/.cache/uv/archive-v0` | 175 | 0.208 ms → 1.189 µs/条 | 0.097 ms → 0.554 µs/条 |
| `~/.cache` | 19 | 0.029 ms → 1.526 µs/条 | 0.014 ms → 0.737 µs/条 |
| `~/Library/Caches` | 142 | 0.145 ms → 1.021 µs/条 | 0.076 ms → 0.535 µs/条 |
| 受控目录（20 个已知文件） | 20 | 0.024 ms → 1.200 µs/条 | 0.013 ms → 0.650 µs/条 |

**解析正确性验证**：`entries` 计数与目录实际条目数**完全吻合**（1,601 / 175 / 19 / 142 / 20），`ERR = 0`，`名字缺失 = 0`。
→ **R2 ADR-04 的三条解析约束全部有效且必要**：我第一版按「`u32 returned + u16 len`」猜布局，1601 项的目录只解析出 **2 条**——按 man page 布局重写后才全部对上。
**这说明 ADR-04 的三条约束是真实存在的坑，不是过度设计**，但 R2 §5.1/ADR-04 **没有写死记录头布局**（`u32 length` 打头、`length` 含自身、下一步 = 指针 + `length`），实现时必须以 man page 为准，建议补进实现说明。

#### (c) 对 R2 §7.2「30 k 条/s」与「118 s 全量」的判断

**判断：「30 k 条/s」严重偏保守（低估约 6～30 倍）；「118 s 全量」因此也偏保守，但 R2 的 5× 余量结论方向是对的、而且过于乐观地乐观。**

逐项对照：

| R2 §7.2 项 | R2 单价 | 实测单价 | 差 |
|---|---|---|---|
| `readdir` 遍历 328 万条目 | 30 k 条/s（冷缓存下限） | **冷 193～674 k 条/s；热 689～911 k 条/s；真冷新建树 3.33 M 条/s** | R2 **低 6～30 倍**（对最保守的冷读也低 6 倍） |
| `getattrlistbulk` ≤ 30 万条 | 3 µs/条 | **0.39～1.53 µs/条**（大目录 0.39） | R2 **高 2～7 倍**（保守） |
| `DT_UNKNOWN` 补 `lstat` 3.3 万次 | 15 µs | 实测 `DT_UNKNOWN = 0` → **该行不应计入** | R2 多算了 0.5 s |
| L0 判定 7.2 万 fd | 15 µs/fd → 1.5 s | 实测 **0.05～0.24 µs/fd（fd 枚举）+ 2.6～2.9 µs/fd（vnode 提取）**，端到端 7～12 ms | R2 **高 200～500 倍** |
| 逐候选 `lstat` ≤ 30 万 | 12 µs | 未单独实测（超出本轮） | 待测 |

**按实测单价重算 328 万条目的 `readdir` 段**：

- 按 R2 的 30 k 条/s：**109 s**（占 118 s 总预算的 92%）；
- 按本机冷缓存实测 193～674 k 条/s：**4.9～17 s**；
- 按本机热缓存实测 700 k 条/s：**4.7 s**；
- 按真冷新建树实测 3.33 M 条/s：**0.1 s**。

**结论**：R2 §7.2 说「`readdir` 遍历是全量扫描的成本主体（109 s / 118 s）」——**这个结构判断在实测下不成立**。实测 `readdir` 只占 4.7～17 s，
**成本主体会转移到「`getattrlistbulk` + 候选归因 + 落盘」这一段**，而 R2 给这几项估的总量只有 0.9 + 2 = **2.9 s**——
**这两项严重低估了**（`getattrlistbulk` 30 万条实测 0.12～0.46 s 没问题，但「归因 / 差分 / 落盘」2 s 要写 30 万条候选的元数据 + 位槽表 + jsonl，实测不可能）。

**修正后的量级估计**（按本机实测单价，同量级 328 万条目 / 30 万候选）：

```
readdir 遍历         328 万条  ×  1.4 µs（热）  ≈  4.7 s   （冷：× 5.2 µs ≈ 17 s）
getattrlistbulk      30 万条  ×  0.4 µs          ≈  0.12 s
逐候选 lstat/symlink 30 万条  ×  12 µs（沿用 R2） ≈  3.6 s
L0 判定              8.5 千 fd × 2.9 µs          ≈  0.03 s  （R2 估 1.5 s）
归因/差分/落盘        30 万候选（按 R2 估的 2 s，实测存疑，真实可能 5～20 s）≈  5～20 s
─────────────────────────────────────────────────────────────────────
合计                                                      ≈ 13 ～ 45 s
```

**所以**：
- **R2 §7.2 的「118 s」偏保守**（实测量级在 13～45 s）；
- **R2 §7.2 的「p95 余量 ≈ 5×」这个结论仍然成立，甚至更宽松**（N1 的上限是 600 s，实测估 118 s 偏保守、真实 13～45 s → 余量 13～46×）；
- **但 R2 §7.2 的「30 k 条/s 是冷缓存下限」这个数字本身该修**——它把冷缓存说成 30 k，实测冷缓存是 193～674 k（真冷新建树 3.33 M）。**修这个数字会连带改变 §7.2 的成本结构**（readdir 从主体降为配角），所以我建议：**不改 §7.2 的结论（结论仍成立），只在 §7.2 加一行「客户端 2026-11-08 实测」**，把单价与成本结构记进去，避免后续按 30 k/s 做容量规划的人误判。

**「118 s 全量」的另一个问题（输入缺失类）**：328 万这个规模假设（V8）在本机没有对应物——
本机 `~/.cache` 全树只有 **93,783 条目**（是 328 万的 1/35），`~/Library/Caches` **115,132 条目**（1/28）。
→ **§7.2 的全量估算在我本机无法直接复现**，只能按单价外推。这个「目标机器上 `~/.cache` 到底有多少条目」是 V8 待确认项，**在目标机器装一次扫描器才知道**。我建议把「目标机实测条目数」列为 V8 的收敛动作（否则 600 s 的 N1 上限在真实规模上是纸面的）。
