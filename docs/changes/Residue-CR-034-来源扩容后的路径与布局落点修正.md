# Residue · CR-034 · 来源扩容后的路径与布局落点修正

- **变更单号**：CR-034
- **状态**：已实施（2026-11-14），待评审
- **来源**：CR-032 代码评审 P2-5 / P2-6 / P2-7；`docs/ledger/Residue-Phase3-闸门台账.md` §四 表项 2b
- **影响契约**：PRD v5.6 AC-01（① 页来源目录）· 视觉基线 v1.1 §三（② 页容器编排）· B1 v1.2 TC-111
- **改动性质**：**落点修正**。不新增页面、不新增来源、不改判定域、不改任何判定算法与文案口径

---

## 一、一句话结论

CR-032 把来源从 3 个扩到 5 个之后，三处「按 3 个来源写死」的落点没跟着改：

① 页显示的是**默认缓存路径**而不是**本轮实际扫的目录**；② 页保护条在 5 个来源下**横向溢出**；
① 页来源网格**硬编码三列**，来源数一变就跟着变形。本单把这三处改成与来源数量无关。

## 二、缺陷（判据 + 实施前现状）

| # | 位置 | 判据 | 实施前 | 判定 |
|---|---|---|---|---|
| **P2-6** | ① 页「来源明细」的「目录」列、② 页保护条 | 显示的路径必须**是这一轮真的扫过的那个目录** | 恒取 `Source.canonicalCachePath`（默认位置） | **不通过**：用户用 `UV_CACHE_DIR` / `npm_config_cache` / `HOMEBREW_CACHE` 搬走缓存后，数值来自新目录、路径却指着旧目录 —— 数值是真的，路径是假的 |
| **P2-5** | ② 页保护边界条 | 保护边界**必须完整可读**：哪几个来源会被自动删除 | 单行 `HStack` + `frame(height: 32)` | **不通过**：标签 + 分隔线 + 五组来源 + 白名单徽标在 751 pt 内装不下（英文更宽），`HStack` 只会压缩/溢出，末尾来源被挤出卡片 |
| **P2-7** | ① 页来源构成网格 | 列数应由**可用宽度**决定，而不是由「当时有几个来源」写死 | `LazyVGrid(columns: count: 3)` | **不通过**：3 个来源时是 3 列、5 个时硬折成 3 + 2；再加来源就是 3 + 3 —— 每格宽窄跟着来源数量变形 |

判据出处：

- P2-6：PRD v5.6 AC-01「① 页列出各来源缓存目录」——「目录」指被扫描的那个目录，
  不是产品文档里的示例路径。
- P2-5：本产品第 3 条核心不变量（不把未知判为安全）的界面侧推论 ——
  **看不见的保护边界等于没有保护边界**。
- P2-7：第 1 条核心不变量（界面禁止算术）的同族问题 —— 视图不该按数据条数切分布局。

## 三、改动清单

### 3.1 P2-6 · 显示本轮实际扫描根

**数据侧**（`ResidueApp/AppModel.swift`）：

- `ScanJob` 新增 `resolvedRoots: [String: String]`：扫描开始时按 `spec.sourceName` 记下
  **实际要扫的路径**（`spec.path`，已含上游命令解析结果与环境变量改动）。
- `AppModel` 新增 `lastResolvedRoots`，扫描收尾时落定，作为 `PageModelBuilder.Input.sourceRoots` 传入。

**取值侧**（`ResidueCore/PageModelBuilder.swift`）：

- `Input` 新增 `sourceRoots: [String: String]`（默认空字典）。
- 两处 `path: source.canonicalCachePath`（来源占比行、重启后「—」行）改为
  `input.sourceRoots[source.rawValue] ?? source.canonicalCachePath`。

**为什么缺项时回退默认路径而不是显示「—」**：回退只发生在「本轮没扫这个来源」时，
那种情况下该行的字节与条数本来就是「—」，路径与数值不会互相冒充；
而默认路径仍是有用信息（用户能据此判断「它本该在哪」）。

### 3.2 P2-5 · 保护条折行

新增布局容器 `WrapHStack`（`ResidueApp/Components.swift`）：

- 按**每个子视图的固有宽度**排布，超出可用宽度才换行；
- **不用 `LazyVGrid`**：保护条每格宽窄差异极大（标签 / 分隔线 / 五组来源 / 徽标），
  等宽网格会把标签也拉成一格宽；
- **视图不参与分组**：折行由布局算，视图只管按顺序摆，符合第 1 条不变量。

保护条改为「左 `WrapHStack`（标签 + 分隔线 + 逐个来源）+ `Spacer` + 右白名单徽标」：

- 白名单徽标 `fixedSize()` 钉在行尾，不参与折行 —— 它是结论，跟着来源挤到第二行会被读成「又一个来源」；
- 高度由 `frame(height: 32)` 改为 `minHeight: 32` + 上下 6 pt 内边距：
  三来源时仍是原来的 32 pt 单行，五来源折两行时条子自己长高，而不是把内容裁掉。

### 3.3 P2-7 · 网格自适应

① 页来源构成网格由 `count: 3` 改为 `GridItem(.adaptive(minimum: 76))`：

- 列数由可用宽度推出，来源增减不用改代码；
- 取 76 pt 而不是更大值，是为了在本页当前可用宽度下**仍然排成三列**
  （与视觉基线设计稿一致），更宽也不会变成两列。

## 七、硬边界（实施后仍然有效）

1. **删除仍只有一条路径**：`TrashExecutor` 原子 rename 到废纸篓，全文无 `rm` / `unlink`。
2. **界面仍不做算术**：P2-5 / P2-7 把「按来源数量切分布局」从视图里拿走，交给布局系统；
   新增的 `WrapHStack` 只做尺寸排布，不碰任何域内度量。
3. **未知仍不显示 0**：P2-6 的回退只影响路径文案，不改变任何取值的「已知 / 未知」判定。
4. **不改判定域、不改门槛**：`GateEvaluator.isQualified` 与 `Source.isInDecisionDomain` 一行未动。
