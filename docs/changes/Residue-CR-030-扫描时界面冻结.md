# CR-030 · 扫描时界面冻结（P1 · 用户直接报的现象）

> **现象**：点击「扫描」后界面**完全卡住** —— 不能拖动、不能滚动、点按钮无反应
> **根因**：`@MainActor` 类上的 `async` 函数**不会自动离开主线程**
> **实测规模**：本机 **222,858 项 ≈ 12.21 秒**的全同步阻塞跑在主线程上
> **性质**：**用户可直接感知的功能缺陷**（不是内部实现问题）
> **状态**：已修 + 三层防线已证伪

---

## 一、根因

### 1.1 `@MainActor` + `async` ≠ 自动离开主线程

原实现：

```swift
@MainActor
@Observable
final class AppModel {
    func runScan(mode: ScanEngine.Mode = .full) async {
        // 整个扫描在这里同步跑
        for (sourceName, root) in roots {
            let result = try engine.scan(root: root, mode: mode, now: started)
            ...
        }
    }
}
```

**关键误解**：很多人以为「标了 `async` 就不会阻塞 UI」。实际上：

> `async` 只让函数**可以被挂起**（在 `await` 处让出执行权）。
> 而函数体里的**同步代码仍在主 actor 上执行**。
>
> `engine.scan(...)` 是**同步调用**，它不会让出 —— 整个 12 秒都占着主线程。

于是：`await Task { await app.runScan() }` → `Task` 继承主 actor 上下文 → 扫描在主线程跑 → **UI 冻结**。

### 1.2 实测规模（本机 · 2026-11-09）

| 来源 | 项数 | 耗时 |
|---|---|---|
| `~/.cache/uv` | 115,875 | **6.44 s** |
| `~/.npm/_npx` | 106,983 | **6.79 s** |
| **合计（一次完整扫描）** | **222,858** | **12.21 s** |

> **注意 `_npx` 只增不减** —— `npx` 每次运行临时工具都会在 `~/.npm/_npx` 下留一个目录。
> 所以**用户用得越多，扫描越慢**，这个卡顿会**随时间加剧**。

## 二、为什么**不是**多线程

这是本轮最需要说清的一点，因为「加多线程」是个很自然的直觉，但**在这里是错的**。

| | 扫描的实际瓶颈 |
|---|---|
| 是什么 | 222,858 次 `stat` / `contentsOfDirectory` —— **元数据查询** |
| 在哪执行 | **内核态**，且磁盘/元数据缓存是**串行竞争**的 |
| 并行化会怎样 | **总时长不变**，只会加剧磁盘竞争、增加上下文切换开销 |

**瓶颈不是「单线程不够快」，而是「在主线程上做 I/O」。**

所以正解是 **「离开主线程」**（actor 隔离），不是 **「加线程」**（并行化）。

> 多线程会把一个**明确的**问题（UI 冻结）变成一个**模糊的**问题（UI 不冻但扫描慢，且难以复现与诊断）。

## 三、修法：三件事，缺一件都还是「像卡住」

| # | 做什么 | 缺了会怎样 |
|---|---|---|
| 1 | **搬走**：重活进 `Task.detached` | 界面**冻住**（原症状） |
| 2 | **汇报**：进度持续回流 | 界面能动但**没反馈** → 用户仍会以为卡死，还会重复点击 |
| 3 | **可取消**：13 秒不能反悔 | 用户被迫等完，且无法中止误点的扫描 |

### 3.1 搬走

`runScan` 拆成「主 actor 内外两段」：

```swift
let job = await Task.detached(priority: .userInitiated) { () -> ScanJob in
    // 重活全在这里：来源根解析、逐来源扫描、L0 探测
}.value
// 回到主 actor：落盘、刷新界面
```

**遇到的三个 Swift 6 并发约束**（都是编译器正确地拒绝了不安全代码）：

| 约束 | 现象 | 解法 |
|---|---|---|
| **`static` 方法也是主 actor 隔离的** | `main actor-isolated static method 'resolveSourceRootsStatic' cannot be called from outside of the actor` | 改成**自由函数**（无 actor 归属）—— 即「要离开主 actor，就不能把它放在主 actor 隔离的类型里」 |
| **`Sendable` 缺失** | `SendingClosureRisksDataRace`（捕获了 `engine`） | 给 `ScanEngine` 声明 `Sendable`（它成员全是 `let` + `Sendable`，**天然不可变**） |
| **`Thread.isMainThread` 在 async 上下文不可用** | `class property 'isMainThread' is unavailable from asynchronous contexts` | 包一层**同步方法**（那一刻真的在执行） |

### 3.2 汇报

`ScanEngine.scan` 新增 `progress` 回调 + `progressEvery` 间隔：

```swift
public struct Progress: Sendable {
    public var source: String
    public var filesScanned: Int
    public var candidatesFound: Int
    public var elapsed: TimeInterval
}
```

**回调频率受控**：每条都回调 = 22 万次跨 actor 跳转，**比扫描本身还贵**。
按 2000 条一次 → 22 万条约 **110 次**，足够让界面「动起来」。

**进度文案不写百分比**：

> 总条目数**事先不知道**（要先扫一遍才知道）→ 百分比是假的。
> 「已扫描 N 项 · 已用时 X 秒」是**能如实说出口**的量。

### 3.3 可取消

`CancelBox`（`@unchecked Sendable` + 锁）：

- 主 actor 写取消信号、后台任务读，**不需要 `await`**（扫描循环里每条都 await 会抵消后台化的收益）
- 语义是「**尽快在下一个检查点停下**」，不是「立刻打断当前这次 I/O」
  （一次 `contentsOfDirectory` 就要几毫秒，I/O 不可中断）
- 契约：`E-104`「用户取消」—— **取消不是失败**，它落断点、且**不计入计数日**（M1）

## 四、防再犯（三层，均已证伪）

### 第 1 层 · 并发单测（`ScanConcurrencyTests`，6 条）

**核心那条 `testScanDoesNotRunOnMainThread`** 直接问「**扫描执行的那一刻在哪个线程上**」：

```swift
XCTAssertEqual(probe.sawMainThread(), false, "扫描跑在了主线程上")
```

> ### 这里踩了一个坑，值得单独记
>
> 第一版是**测响应延迟**（造大目录 → 扫描时主 actor 反复 `Task.yield()` → 断言最大延迟 < 阈值）。
> **它测不出差别** —— 证伪时把扫描放回 `@MainActor` 竟然**仍然通过**：
>
> - 造 3000 个文件 → 扫描只要 0.12 s → 比阈值（2 s）还快 → 两种实现都过
> - 造 6 万个文件 → 造数本身要几秒 → **测试超时（SIGTERM）**
>
> **根因**：要靠时间阈值区分，就必须让「扫描耗时 >> 阈值」，而造出那个规模的样本**本身就贵到不可接受**。
>
> **正解**：测「**机制**」而不是「**后果**」——
> 后者会随机器、随缓存大小、随文件系统缓存命中率而漂移。
>
> 这是本项目「**把实现改错，这条断言会红吗？**」这条判据的又一次应用：
> 时间阈值那条**改错了不会红**，所以它不构成防线。

其余 5 条：主 actor 可调度 / 进度被汇报 / 回调频率受控 / 进度计数单调 / 取消令牌可传递。

### 第 2 层 · 接线自检（`WiringSelfCheck` 新增 §4c2，4 项）

真走一遍：后台扫描 → 主 actor 让出-恢复 → 进度被汇报 → 取消信号可传递。

### 第 3 层 · 静态断言（`verify_a9` 新增第十三节，7 项）

钉住代码形态（因为这类缺陷**单测看不出来**——单测不渲染界面）：

1. `ScanEngine` 必须声明 `Sendable`
2. `runScan` 里必须有 `Task.detached`
3. `ScanEngine` 不得被 `@MainActor` 隔离
4. 扫描引擎必须支持进度回调
5. 界面必须显示进度
6. 界面必须提供取消
7. **所有 `engine.scan` 调用必须在 `Task.detached` 块内**

## 五、两处判据自身写错了（已修）

这轮又出现「**校验脚本自己说谎**」，累计第 5 次：

### 5.1 静态断言按行匹配，区分不出「在后台」与「在主 actor」

第一版判据是「grep 有没有 `let x = try engine.scan(`」——
但**合法的那个调用也在 detached 块里**（只是缩进更深），
按行匹配根本区分不了。证伪时注入了「主 actor 上直接调 `engine.scan`」，**断言没报红**。

**正解**：按**缩进层级**判定 —— 调用所在行的缩进必须 **>** detached 起始行的缩进。

### 5.2 修完第一版反而误报（不等号方向写反）

改对逻辑后，正确代码上又报了「1 处不在 detached 块内」。
查下来是 `di > indent` 写反了 —— 应该是 `indent > di`。

**两次都在同一条断言上**。这印证了本项目的老教训：
> **判据不可靠，两个方向都会出错。**
> 写完必须**证伪两次**：注入缺陷要红、正确代码要绿。

## 七、为什么这轮没有加「增量扫描」

`ScanEngine.Mode` 已经有 `.incremental`（不发现深层新候选），但**产品没在用它** ——
用户看到「扫描」就走全量。

**这是产品决定，不是实现缺陷**：全量才能发现新的深层候选。
但考虑到 `_npx` 目录只增不减，**增量扫描的收益会越来越大**。

**已登记为上线后优化项**（需产品裁定量化口径：增量扫描多久跑一次、漏了深层候选怎么补）。
