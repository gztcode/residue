# CR-031 · 结算链路写入（P0 · 产品永远点不亮的最后一环）

> **缺陷**：门槛链的**三个门槛量** `K`（样本）/ `a`（L0 误判）/ `producedAt`（报告产出）
> 在运行路径上**从未被写过非空值** → `GateEvaluator.isQualified` 恒 `false`
> → 自动删除**永远点不亮**，产品退化为只读扫描器
> **契约依据**：PRD v5.5 · 指标定义表 M1/M3/M4/M5 / AC-08 / AC-09；R2 v1.8 §5.1 / §5.5 / §7.3 / §7.4
> **性质**：**功能缺失**（不是接线遗漏，也不是实现错误）
> **状态**：**待受理**（本文档为变更单，实现须在本单受理后开始）
>
> **修订记录（v2 · 2026-11-14）**：经六路独立审计交叉核对，初稿有**三处事实错误**已改正：
> ① `a` 并非「已有实现」——它同样恒为 0；② 336 MB 规模冲突**契约里早已登记为 D-03**，
> 不是本单新发现；③ 「快照清单完全不存在」过强——`Slots` 段确含候选级 `path + birthtime`，
> 缺的是**以快照语义冻结的成员集合**。

## 一、缺陷事实（全部经代码与契约双向核对）

### 1.1 门槛链断在 `K`

`GateEvaluator.isQualified` 的三项门槛（PRD AC-08 组 B）：

```swift
guard let k = input.attributable, let t = input.total else { return false }
if k < Threshold.h(forTotal: t) { return false }
guard let a = input.missCount, a == 0 else { return false }
guard let b = input.checkCount, b >= 1 else { return false }
```

`input.attributable` 来自 `header.sources[i].K`（`PageModelBuilder.swift:218`）。
而 `K` 在整个 `Sources/` 下**只有一个赋值点**：

```swift
// AppModel.swift · persist()
SourceHeaderEntry(
    source: source,
    snapshotTaken: ...,
    T: ...,
    K: nil, J: nil,          // ← 恒为 nil
    ...
)
```

**结论**：`guard let k = input.attributable` 恒失败 → `isQualified` 恒 `false`
→ `a`、`b`、`T`、`H` 全都算对了也没有意义。

### 1.1b 附带发现：两处 `nil` 被当 `0`（违反不变量③）

`PageModelBuilder.swift:493` 与 `:524`：

```swift
.ratio(entry.K ?? 0, entry.T ?? 0)          // ③ 列
let k = entry.K ?? 0, t = entry.T ?? 0      // ⑦ 结论
```

两处都在 `produced == true` 分支内。若报告已产出而 `K` 仍为 `nil`
（旧载体、或结算写入中途失败），界面会显示「样本 0 / 总量 T」并把结论
判成「未达标」。

契约要求 `nil` 呈现为 `—`（`nil ≠ 0`：0 会被读成「一条都没归因成功」，
那是**另一件事**）。本单修 `K` 写入时**一并**把这两处改成 `.unavailable`。

### 1.2 结算报告从未产出

`settlement.producedAt` 被 `PageModelBuilder.swift:166` 读取（`settlementProduced`），
但 `SettlementHeader.producedAt` 在 `Sources/` 下**从未被写入过**。

`GateEvaluator` 两处都先判 `guard settlementProduced`，于是：

| 量 | 现状 | 后果 |
|---|---|---|
| `T` | 已正确赋值（首次 full 扫描） | 正常 |
| `H` | `min(30, T)`，已赋值 | 正常 |
| **`K`** | **恒 nil**（无写入路径） | **门槛永不成立** |
| **`J`** | **恒 nil** | ⑤ 页 ③ 列三数不齐（`K + J = T` 不可验） |
| **`a`** | **恒 0**（见 §1.4） | 门槛看似满足，实为「没观测过」 |
| **`b`** | 有赋值，但**是覆盖写不是累计**（见 §1.5） | 与 M5 口径不符 |
| **`producedAt`** | **恒 nil** | 观察期永不「已满」 |

### 1.4 `a` 同样没有写入路径（**初稿此处写错，已改正**）

初稿写「`a` 已有实现，本单不动」——**这是错的**。代码反证：

| 检查 | 结果 |
|---|---|
| `MissCounter.apply` 在 `Sources/` 的调用点 | **0 处**（只在 `MetricsTests.swift` 里被调用） |
| `entry.a = ` 赋值 | **0 处**（`self.a = a` 是初始化器形参；`entry.a` 全是读取） |
| `SourceL0State` 被谁持有 | 只有未投产的 `StateStore`（`state.json`，生产零实例化） |
| `SourcePayload`（`F` 位图 / `C_done` / 位槽表） | **生产代码从不写入**（`AppModel.swift:1312` 原样传回，唯一赋值在 `decode` 内） |

**后果**：`a` 恒为 0。而 `a = 0` 是门槛项——于是门槛看起来「满足」，
实际上是**从未观测过**。这比 `K` 恒 nil 更危险：`K` 恒 nil 会让产品点不亮
（安全），`a` 恒 0 会让**本该被拦住的点亮放行**（不安全）。

**本单必须同时修 `a` 的写入路径**，否则只修 `K` 会让门槛在「`a` 从未被观测」
的前提下成立——那等于伪造安全凭证（不变量④）。

### 1.5 `b` 是覆盖写，不是 M5 要求的累计

M5 口径：`b` = 本轮内对该来源**全部候选执行 L0 判定的次数之和**，
**同日重扫重复计数**。

代码（`AppModel.swift:1287`）：

```swift
entry.b = bCount      // bCount = 本次扫描的候选数 —— 覆盖上一次的值
```

于是同一天扫两次，`b` 不会变成 `2 × N`，而是**仍是 `N`**。
这不影响「`b ≥ 1`」这条门槛的成立与否，但让 `b` 的读数与契约不符
（第 ⑤ 页显示的是「最近一次扫描数」，不是「本轮累计检查次数」）。

### 1.6 中断扫描仍推进计数日（**上轮改动邻近的缺陷**）

`AppModel.swift:682` 无条件调用 `advanceCountedDayIfNeeded(now:)`，
而 `job.abortReason` 到 `:734` 才被处理。于是：

> 用户点「取消扫描」→ 扫描被中断 → **计数日照样 +1**

违反 M1：「扫描失败 / 跳过 / 低电量**不计入计数日**」。
`ScanEngine.swift:610` 的注释也明写「中断不计入计数日」。

后果：用户取消 14 次，观察期就「满」了——而实际一次完整观察都没有。
**这是安全性缺陷**（观察期是「证明自己判得准」的唯一手段，被取消动作消耗掉）。

### 1.3 快照候选清单没有持久化（**这是本单的核心难点**）

契约 M3 对 `K` 的定义是**逐条归因的结果**：

> `K` = 该快照内**仍可归因**（未被排除）的条目数
> **`K` 只能由「快照条目逐条归因结果」直接得出，`J` 由 `T − K` 派生**

要逐条归因，必须先有「快照里到底有哪几条」。而载体里的 `SourcePayload` 是：

```swift
public struct SourcePayload {
    public var bitmap: Data              // F 位图（按位槽）
    public var countedDoneSlots: [UInt32] // C_done（槽号）
    public var slots: [UInt32: CandidateID] // 位槽占用表：槽号 → 身份键
}
```

`slots` **看起来**像快照清单，但两者语义不同：

| | `slots`（位槽占用表） | 契约要求的「快照清单」 |
|---|---|---|
| 增长时机 | **每次** L0 判定阴性时分配 | **本轮首次成功扫描**时一次性确定 |
| 是否回收 | 永不回收（含已手删的） | 固定为快照那一刻的集合 |
| 跨版本 | 随 `a` 清零 | 随 `K` 清零 |
| 用途 | `F` 位图的下标 | `K` 的分母 |

**不能拿 `slots` 冒充快照清单**：它含历史上出现过、但快照时刻并不存在的候选
（用户早先删掉的、上一轮遗留的），会**系统性放大 `T`** → `H = min(30, T)` 偏大
→ 门槛偏严；同时让「失联」把从未进过快照的条目也算进去 → `J` 虚高。

> **措辞更正（v2）**：初稿写「快照候选清单**没有**持久化」——过强。
> 准确说法是：**没有以「快照」语义冻结的成员集合**。
> `Slots` 段确实持久化了每个候选的 `path + birthtime`（候选级信息），
> R2 §7.3 还明确用它作增量扫描的「已登记候选」。缺的不是「候选信息」，
> 而是「**哪一批候选属于本轮快照**」这个冻结时刻的集合。
>
> 另外，生产代码**从不写入 `SourcePayload`**（`AppModel.swift:1312` 原样传回，
> 唯一赋值在 `decode` 内）——所以连 `Slots` 段当前都是空的。
> 这一条与 §1.4 的 `a` 未接线是同一个根因。

## 二、契约对归因的规定（逐条摘录，作为实现验收依据）

### 2.1 `K` 的算法（M3 · 唯一式）

- **`K + J = T`** 是恒等式；`J = T − K` 是**派生量**
- **禁止**任何第二套算法：不得 `K = T − J` 与独立算 `K` 并存
- **禁止** `K = T − J − 重建数`
- **不得由 `J` 反推 `K`**（否则恒等式循环恒真、不可证伪）

### 2.2 失联四类（M3 · 只作标签，不参与计数）

| 类别 | 判定 | 是否改变 `J` |
|---|---|---|
| 改名 | 同 inode / birthtime 出现在新路径 | 否（只打标签） |
| 用户手删 | 路径不存在且无同名重建 | 否 |
| 目录拆分合并 | 父目录结构变化导致路径失效 | 否 |
| 无法归因 | 以上都不匹配 | 否（兜底） |

**关键**：「四类只作归因标签、不参与计数、不改变 `J`」——
`J` 只由 `T − K` 派生，标签只用于报告说明。

### 2.3 身份键 = `path + birthtime`

- 路径相同 + birthtime 变化 = **同名重建**：旧条目留在本轮（计入 `J`），
  新条目**转入下一轮快照**，不计入本轮样本
- 「用户手删」的条目已不存在，**下一轮不会进入新快照**——不得声称「失联条目下一轮重新计入」

### 2.4 结算时刻（M1 / M3）

- **`T`**：本轮首次成功 `full` 扫描完成时刻（已有实现，正确）
- **`K`**：观察期结束扫描时写入（冻结值）
- **观察期已满** ⟺ 第 14 个计数日结束后的**第一次成功扫描**已完成
  **且该次扫描同时产出了 AC-09 报告**
- **计数日封顶 14**（`15/14` 永不出现）

### 2.5 `pipx` 行例外

`pipx` run 属**非判定域**，**不取快照** → 该行 `J` 无非零来源
→ **不套用 `K + J = T`**（否则该断言对该行恒真、无判别力）。

## 三、拟改范围

### 3.1 新增：快照清单（Core）

在 `SourcePayload` 增加**第 4 项**（与 `bitmap` / `countedDoneSlots` / `slots` 并列）：

```swift
/// 本轮快照的候选清单（`T` 的成员，逐条归因的对象）。
///
/// **只在「本轮首次成功 full 扫描」时写入一次**，此后冻结。
/// 与 `slots` 的区别见 CR-031 §1.3 —— 不能互相顶替。
public var snapshotMembers: [CandidateID]
```

- 载体 schema 版本 **1 → 2**（新增字段，旧载体走既有 `E-301` 只读降级路径
  还是就地升级，需在受理时裁决 —— 见 §五 待决项）
- 规模：300 万候选 × ~100 B ≈ 300 MB 量级。**这与契约「载体约 1 MB 量级」
  （M4 · 载体规模口径）冲突** —— 见 §五 待决项 ①

### 3.2 新增：归因判定（Core，纯函数，可单测）

```swift
public enum Settlement {
    public struct Attribution: Sendable {
        public var candidate: CandidateID
        public var status: Status       // .attributable / .lost(Label)
    }
    public enum Label: String, Sendable {
        case renamed, userDeleted, directoryRestructured, unattributable
    }

    /// 逐条归因。`K` 由结果直接得出，`J = T − K` 派生。
    public static func attribute(
        snapshot: [CandidateID],
        current: [CandidateID],
        fileSystem: ...
    ) -> [Attribution]
}
```

**判据（必须按契约，不得自创）**：

| # | 情形 | 归因结果 |
|---|---|---|
| 1 | 身份键（`path + birthtime`）在 `current` 中 | `.attributable` |
| 2 | 路径**相同**但 `birthtime` 变化（**同名重建**） | `.lost(.directoryRestructured)` |
| 3 | 同 `inode` / `birthtime` 出现在**新路径**（改名） | `.lost(.renamed)` |
| 4 | 路径不存在、同目录无同名重建 | `.lost(.userDeleted)` |
| 5 | 父目录结构变化导致路径失效 | `.lost(.directoryRestructured)` |
| 6 | `lstat` 失败（权限 / 跨 uid） | `.lost(.unattributable)`（见 §五③） |
| 7 | 以上都不匹配 | `.lost(.unattributable)` |

> **第 2 行的标签是契约指定的，不是我们挑的**：M3 算法行明写
> 「同名重建命中的条目**计入 `J`**（归因标签为「目录拆分合并」类之一）」。
> 初稿漏了这一行，会让同名重建落到第 7 行「无法归因」——与契约冲突。
>
> **第 2 行还决定了一件事**：重建后的**新条目转入下一轮快照**、不计入本轮样本。
> 所以本轮 `K` 不含它，下一轮 `T` 才会把它算进去。

### 3.3 新增：结算写入（AppModel）

在「观察期结束扫描」这一时刻：

1. 逐条归因 → `K`
2. `J = T − K`（派生，不独立算）
3. 写 `entry.K` / `entry.J` / `entry.snapshotDate` / `entry.settlementDate`
4. 写 `settlement.producedAt` / `reportId`
5. **同一次原子写入**落盘（不得分成两次 —— 否则会出现「`K` 非 nil 但
   `producedAt` nil」：界面显示未结算而门槛已在用 `K`）

**触发条件**（M1）：`countedDays == 14` 且本次扫描**成功且未中断** → 这次就是结算扫描。

### 3.4 修复：`a` 的写入路径（**本单必做，不可推迟**）

`MissCounter` 已存在且有单测，但**生产零调用**。要接上：

1. 每次扫描后，用 L0 快照对每条候选做一次判定
2. `F` 置位（首检阴性）、`P_now` 求取、`C_done` 并入、`a` 累加
   —— 四者**同一次扫描内一次性完成**（M4「统一时点」）
3. 写 `entry.a`，并把 `F` / `C_done` / 位槽表写进 `SourcePayload`（**当前从不写入**）

**为什么不能推迟**：`a` 恒 0 会让门槛在「从未观测」的前提下成立 ——
那是伪造安全凭证（不变量④）。只修 `K` 不修 `a`，等于把产品从
「点不亮」改成「**不安全地点亮**」，比现状更糟。

### 3.5 修复：`b` 改为累计（M5）

```swift
entry.b += bCount     // 本轮内累加；轮次切换时归零
```

### 3.6 修复：中断扫描不推进计数日（M1）

把 `advanceCountedDayIfNeeded` 移到「确认本次扫描成功且未中断」之后，
并**同时**修 §1.7-f（中断的 full 扫描不得用部分 candidates 取 `T`）。

### 3.7 接线自检 + 单测

- 单测：归因七种情形各一例、`K + J = T` 恒等、同名重建不计入本轮、
  `pipx` 行不套恒等式、`a` 的逐候选判据（含 `C_done` 去重）、
  `b` 累计、中断不推进计数日
- 接线自检：真文件系统造快照 → 删几条 → 结算 → 断言 `K`/`J` 与预期一致；
  再断言 `a` / `b` / `producedAt` 非空且自洽

### ① 快照清单的存储位置（**规模冲突契约里已登记，不是本单新发现**）

> **重要更正（v2）**：初稿把「300 MB vs 1 MB」写成本单的新发现 —— **这是错的**。
>
> R2 v1.8 `:733` 已经把它登记为 **PM 裁决项 D-03**：

> > 「约 1 MB 量级」**不一致**（那个量级只算 `F` 位图）→ **PM 裁决项 D-03**」

> （`112 B/条`，见 `:782`）。
>
> 也就是说：**载体规模冲突在契约内部早已存在且已登记**，与本单无关。
> 本单真正要裁决的只有一件事：**快照成员集合放在哪**。

因为 D-03 尚未裁决，本单**不重开规模之争**，只提出一个不与 D-03 冲突的方案：

| 选项 | 做法 | 与 D-03 的关系 |
|---|---|---|
| **A（建议）** | 快照成员集合落 `state/snapshot-<round>.json`，**不进 `state.residue`** | **绕开 D-03**：载体规模不变，D-03 的 336 MB 仍按原样等 PM 裁决 |
| B | 复用位槽表 + 「快照轮次戳」，只记快照那一刻已分配的槽号 | 仍受 D-03 约束（槽表本身就在 336 MB 里） |
| C | 接受载体变大，修订 M4 口径 | **等于替 PM 做 D-03 的裁决**，超出本单权限 |

**建议 A 的理由**：它把「快照成员」与「`a` 的载体」解耦，两件事各自演进；
且 `state/` 下已有 `schedule.json` / `checkpoints.json` 先例，不是新机制。
代价是需要第二张单把 `state/snapshot-*.json` 登记进 N7 清除范围（含候选路径）。

**B 为什么不行**（需要写清，否则会被当成省事方案）：位槽号**只增不回收**
（M4 / CR-021 明文），所以「槽号 ≤ N」无法区分「快照时已存在」与
「快照后才分配」——无法还原快照集合。

### ② 旧载体的迁移

schema 1 → 2。旧载体没有 `snapshotMembers`：

- 若走 `E-301` 只读降级 → 老用户升级后**整个观察期作废**（`T` 也没了）
- 若就地升级 → 首次扫描重新取快照（`T` 重置），观察期从头开始

两者都让老用户重来。**需要裁决**：是否接受「升级即重置观察期」。
（注：这与「应用版本变更重置观察期」的既有规则一致，可能是可接受的。）

> **但迁移路径本身有个既有缺陷必须先修**（审计发现，已核实）：
> `clearCarrierForVersionChange` 造的是**全新 `StateHeader()`**，
> 只把 `appVersion` / `round` 填回去 —— 于是 `autoDeleteEnabled` 被
> **静默置 `false`**、`sources` 被清空。
>
> 后果：用户升级一次，**已经点亮的自动删除开关被悄悄关掉**，而界面不会
> 提示原因。这不是「重置观察期」，是「丢失用户设置」。
>
> 迁移实现必须改成「保留 `autoDeleteEnabled` 等用户设置，只清凭证类字段」。

### ③ 归因需要读文件系统，与「不把未知判为安全」

归因要 `lstat` 每个快照候选。若 `lstat` 失败（权限、跨 uid）：

- 判 `.attributable` → **把未知判为安全**（违反不变量③）
- 判 `.lost` → `K` 偏小 → 门槛偏严（保守，但可能让用户永远点不亮）

**我的建议：判 `.lost(.unattributable)` 并在报告里如实标注**。
保守方向正确（宁可点不亮，不可误判可删），但要在 UI 上说清「有 N 条无法归因」。

## 六、验收判据（本单完成的定义）

| # | 判据 | 验证方式 |
|---|---|---|
| 1 | `K` 在结算扫描后非 nil | 单测 + 接线自检 |
| 2 | `K + J = T` 恒成立 | 单测（含边界：全失联 / 零失联） |
| 3 | 同名重建（path 同、birthtime 变）计入 `J` 不计入 `K`，标签为「目录拆分合并」 | 单测（真文件系统） |
| 4 | 用户手删不计入 `a`，计入 `J` | 单测 |
| 5 | `pipx` 行不套 `K + J = T` | 单测 |
| 6 | 结算后 `settlement.producedAt` 非 nil | 接线自检 |
| 7 | 结算后门槛可成立（构造 `K ≥ H` ∧ `a = 0` ∧ `b ≥ 1`） | 单测 |
| 8 | 旧载体升级不崩溃、不静默丢数据 | 单测 |
| **9** | **`a` 有真实写入路径**：造一条「曾判阴性、后被持有」的候选 → `a` 变 1 | 单测 + 接线自检 |
| **10** | **`a` 的同候选不重复计**：持续持有跨多次扫描，`a` 仍为 1 | 单测 |
| **11** | **`b` 是累计**：同日扫两次，`b` 为两次之和 | 单测 |
| **12** | **中断扫描不推进计数日**：取消一次后 `countedDays` 不变 | 单测 + 接线自检 |
| **13** | **中断的 full 扫描不取 `T`** | 单测 |
| **14** | **`K`/`J`/`producedAt` 原子写入**：不存在「`K` 非 nil 而 `producedAt` nil」的中间态 | 单测 |

判据 9–14 是 v2 新增：它们对应初稿**误判为「已有实现」或「不在范围」**的三处缺陷。
只做 1–8 会让产品「安全地不点亮」，而 9–14 才让它「**正确地**点亮」。

## 七、为什么这张单必须先受理

两个理由：

**① 契约层面有未裁决项。** 快照成员集合放在哪，与 D-03（载体规模）相关。
按本仓库规矩（CLAUDE.md §五）：

> 代码与文档对不上就是缺陷，不是「文档过时了」。
> 改契约需要变更单。

若选方案 A（独立落 `state/snapshot-*.json`），需要第二张单把它登记进
N7 清除范围——因为该文件**含候选路径**，漏清就等于「清除后仍留用户路径副本」。

**② 范围比初稿大。** 初稿以为只缺 `K`；审计核对后发现 `a`、`b`、计数日
三处也不符合契约。这不是「顺手多修」，而是**不修就不能算完成**：
只修 `K` 会让门槛在 `a` 从未被观测的前提下成立，比现在更不安全。

因此本单需要你裁决的是：

| 待决项 | 需要你决定 |
|---|---|
| §五① | 快照成员落哪（建议 A：独立文件） |
| §五② | 旧载体迁移策略（观察期重置是否可接受） |
| §五③ | 归因 `lstat` 失败时判什么（建议 `.lost(.unattributable)`） |
| §三新增 | 是否同意把 `a` / `b` / 计数日三处一并纳入本单（建议纳入） |
