## 一、缺陷事实（全部经代码与契约双向核对）

> **时点说明**：本节记录的是**受理时**的事实快照 ——
> 表格里的「0 处」「恒为 0」都是**当时**的实测值。
> 本单实施后的状态见 **§九**，实施期新发现的缺陷见 **§八**。

### 1.1 门槛链断在 `K`

`GateEvaluator.isQualified` 的三项门槛（PRD AC-08 组 B）：

```swift
guard let k = input.attributable, let t = input.total else { return false }
if k < Threshold.h(forTotal: t) { return false }
guard let a = input.missCount, a == 0 else { return false }
guard let b = input.checkCount, b >= 1 else { return false }
```

`input.attributable` 来自 `header.sources[i].K`（`PageModelBuilder.swift:218`）。
而 `K` 在整个 `Sources/` 下**只有一个赋值点**：

```swift
// AppModel.swift · persist()
SourceHeaderEntry(
    source: source,
    snapshotTaken: ...,
    T: ...,
    K: nil, J: nil,          // ← 恒为 nil
    ...
)
```

**结论**：`guard let k = input.attributable` 恒失败 → `isQualified` 恒 `false`
→ `a`、`b`、`T`、`H` 全都算对了也没有意义。

### 1.1b 附带发现：两处 `nil` 被当 `0`（违反不变量③）

`PageModelBuilder.swift:493` 与 `:524`：

```swift
.ratio(entry.K ?? 0, entry.T ?? 0)          // ③ 列
let k = entry.K ?? 0, t = entry.T ?? 0      // ⑦ 结论
```

两处都在 `produced == true` 分支内。若报告已产出而 `K` 仍为 `nil`
（旧载体、或结算写入中途失败），界面会显示「样本 0 / 总量 T」并把结论
判成「未达标」。

契约要求 `nil` 呈现为 `—`（`nil ≠ 0`：0 会被读成「一条都没归因成功」，
那是**另一件事**）。本单修 `K` 写入时**一并**把这两处改成 `.unavailable`。

### 1.2 结算报告从未产出

`settlement.producedAt` 被 `PageModelBuilder.swift:166` 读取（`settlementProduced`），
但 `SettlementHeader.producedAt` 在 `Sources/` 下**从未被写入过**。

`GateEvaluator` 两处都先判 `guard settlementProduced`，于是：

| 量 | 现状 | 后果 |
|---|---|---|
| `T` | 已正确赋值（首次 full 扫描） | 正常 |
| `H` | `min(30, T)`，已赋值 | 正常 |
| **`K`** | **恒 nil**（无写入路径） | **门槛永不成立** |
| **`J`** | **恒 nil** | ⑤ 页 ③ 列三数不齐（`K + J = T` 不可验） |
| **`a`** | **恒 0**（见 §1.4） | 门槛看似满足，实为「没观测过」 |
| **`b`** | 有赋值，但**是覆盖写不是累计**（见 §1.5） | 与 M5 口径不符 |
| **`producedAt`** | **恒 nil** | 观察期永不「已满」 |

### 1.4 `a` 同样没有写入路径（**初稿此处写错，已改正**）

初稿写「`a` 已有实现，本单不动」——**这是错的**。代码反证：

| 检查 | 结果 |
|---|---|
| `MissCounter.apply` 在 `Sources/` 的调用点 | **0 处**（只在 `MetricsTests.swift` 里被调用） |
| `entry.a = ` 赋值 | **0 处**（`self.a = a` 是初始化器形参；`entry.a` 全是读取） |
| `SourceL0State` 被谁持有 | 只有未投产的 `StateStore`（`state.json`，生产零实例化） |
| `SourcePayload`（`F` 位图 / `C_done` / 位槽表） | **生产代码从不写入**（`AppModel.swift:1312` 原样传回，唯一赋值在 `decode` 内） |

**后果**：`a` 恒为 0。而 `a = 0` 是门槛项——于是门槛看起来「满足」，
实际上是**从未观测过**。这比 `K` 恒 nil 更危险：`K` 恒 nil 会让产品点不亮
（安全），`a` 恒 0 会让**本该被拦住的点亮放行**（不安全）。

**本单必须同时修 `a` 的写入路径**，否则只修 `K` 会让门槛在「`a` 从未被观测」
的前提下成立——那等于伪造安全凭证（不变量④）。

### 1.5 `b` 是覆盖写，不是 M5 要求的累计

M5 口径：`b` = 本轮内对该来源**全部候选执行 L0 判定的次数之和**，
**同日重扫重复计数**。

代码（`AppModel.swift:1287`）：

```swift
entry.b = bCount      // bCount = 本次扫描的候选数 —— 覆盖上一次的值
```

于是同一天扫两次，`b` 不会变成 `2 × N`，而是**仍是 `N`**。
这不影响「`b ≥ 1`」这条门槛的成立与否，但让 `b` 的读数与契约不符
（第 ⑤ 页显示的是「最近一次扫描数」，不是「本轮累计检查次数」）。

### 1.6 中断扫描仍推进计数日（**上轮改动邻近的缺陷**）

`AppModel.swift:682` 无条件调用 `advanceCountedDayIfNeeded(now:)`，
而 `job.abortReason` 到 `:734` 才被处理。于是：

> 用户点「取消扫描」→ 扫描被中断 → **计数日照样 +1**

违反 M1：「扫描失败 / 跳过 / 低电量**不计入计数日**」。
`ScanEngine.swift:610` 的注释也明写「中断不计入计数日」。

后果：用户取消 14 次，观察期就「满」了——而实际一次完整观察都没有。
**这是安全性缺陷**（观察期是「证明自己判得准」的唯一手段，被取消动作消耗掉）。

### 1.3 快照候选清单没有持久化（**这是本单的核心难点**）

契约 M3 对 `K` 的定义是**逐条归因的结果**：

> `K` = 该快照内**仍可归因**（未被排除）的条目数
> **`K` 只能由「快照条目逐条归因结果」直接得出，`J` 由 `T − K` 派生**

要逐条归因，必须先有「快照里到底有哪几条」。而载体里的 `SourcePayload` 是：

```swift
public struct SourcePayload {
    public var bitmap: Data              // F 位图（按位槽）
    public var countedDoneSlots: [UInt32] // C_done（槽号）
    public var slots: [UInt32: CandidateID] // 位槽占用表：槽号 → 身份键
}
```

`slots` **看起来**像快照清单，但两者语义不同：

| | `slots`（位槽占用表） | 契约要求的「快照清单」 |
|---|---|---|
| 增长时机 | **每次** L0 判定阴性时分配 | **本轮首次成功扫描**时一次性确定 |
| 是否回收 | 永不回收（含已手删的） | 固定为快照那一刻的集合 |
| 跨版本 | 随 `a` 清零 | 随 `K` 清零 |
| 用途 | `F` 位图的下标 | `K` 的分母 |

**不能拿 `slots` 冒充快照清单**：它含历史上出现过、但快照时刻并不存在的候选
（用户早先删掉的、上一轮遗留的），会**系统性放大 `T`** → `H = min(30, T)` 偏大
→ 门槛偏严；同时让「失联」把从未进过快照的条目也算进去 → `J` 虚高。

> **措辞更正（v2）**：初稿写「快照候选清单**没有**持久化」——过强。
> 准确说法是：**没有以「快照」语义冻结的成员集合**。
> `Slots` 段确实持久化了每个候选的 `path + birthtime`（候选级信息），
> R2 §7.3 还明确用它作增量扫描的「已登记候选」。缺的不是「候选信息」，
> 而是「**哪一批候选属于本轮快照**」这个冻结时刻的集合。
>
> 另外，生产代码**从不写入 `SourcePayload`**（`AppModel.swift:1312` 原样传回，
> 唯一赋值在 `decode` 内）——所以连 `Slots` 段当前都是空的。
> 这一条与 §1.4 的 `a` 未接线是同一个根因。

## 二、契约对归因的规定（逐条摘录，作为实现验收依据）

### 2.1 `K` 的算法（M3 · 唯一式）

- **`K + J = T`** 是恒等式；`J = T − K` 是**派生量**
- **禁止**任何第二套算法：不得 `K = T − J` 与独立算 `K` 并存
- **禁止** `K = T − J − 重建数`
- **不得由 `J` 反推 `K`**（否则恒等式循环恒真、不可证伪）

### 2.2 失联四类（M3 · 只作标签，不参与计数）

| 类别 | 判定（编号见 §3.2 判据表） | 是否改变 `J` |
|---|---|---|
| 改名 | ③ 路径不同、同 `birthtime` 在当前结果中**唯一**命中一条 | 否（只打标签） |
| 用户手删 | ⑥ 无同 `birthtime` 命中者，且**父目录仍存在可读**、该路径**确定已不存在** | 否 |
| 目录拆分合并 | ② 路径相同但 `birthtime` 变化（**同名重建**）<br>⑦ 父目录**确定已不在**，或该路径**仍在但已不再是候选** | 否 |
| 无法归因 | ④ 同 `birthtime` **命中不止一条**（匹配不唯一）<br>⑤ 该路径**不可读**（`lstat` 失败）<br>兜底 **父目录不可读** | 否（兜底） |

**关键**：「四类只作归因标签、不参与计数、不改变 `J`」——
`J` 只由 `T − K` 派生，标签只用于报告说明。

### 2.3 身份键 = `path + birthtime`

- 路径相同 + birthtime 变化 = **同名重建**：旧条目留在本轮（计入 `J`），
  新条目**转入下一轮快照**，不计入本轮样本
- 「用户手删」的条目已不存在，**下一轮不会进入新快照**——不得声称「失联条目下一轮重新计入」

### 2.4 结算时刻（M1 / M3）

- **`T`**：本轮首次成功 `full` 扫描完成时刻（已有实现，正确）
- **`K`**：观察期结束扫描时写入（冻结值）
- **观察期已满** ⟺ 第 14 个计数日结束后的**第一次成功扫描**已完成
  **且该次扫描同时产出了 AC-09 报告**
- **计数日封顶 14**（`15/14` 永不出现）

### 2.5 `pipx` 行例外

`pipx` run 属**非判定域**，**不取快照** → 该行 `J` 无非零来源
→ **不套用 `K + J = T`**（否则该断言对该行恒真、无判别力）。

## 三、拟改范围

### 3.1 新增：快照清单（Core）

**裁决结果（§五①）：落在 `state.residue` 内，作为每来源的第 4 个段。**

在 `SourcePayload` 增加**第 4 项**（与 `bitmap` / `countedDoneSlots` / `slots` 并列）：

```swift
/// 本轮快照的候选清单（`T` 的成员，逐条归因的对象）。
///
/// **只在「本轮首次成功 full 扫描」时写入一次**，此后冻结。
/// 与 `slots` 的区别见 CR-031 §1.3 —— 不能互相顶替。
public var snapshotMembers: [CandidateID]
```

- 载体 schema 版本 **1 → 2**（新增段 kind `0x04`）
- 段顺序固定：`F` → `C_done` → `Slots` → `Snapshot`（按 `(sourceIndex, kind)` 索引，
  不按位置；顺序固定只为可读性）
- 规模：300 万候选 × ~100 B ≈ 300 MB 量级。**这与原契约「载体约 1 MB 量级」
  （M4 · 载体规模口径）冲突** —— 按裁决 ①，**M4 口径随本次修订**
  （PRD v5.6 §M4「载体规模口径」行），**D-03 随之关闭**
- **N7 清除范围不变**：`state.residue` 本来就**不属 N7 的 `.jsonl` 记录目录**，
  不计入 N7 计量与容量回收，「一键清除」不作用于它 → 快照清单含候选路径
  **不引入新的隐私类**，**不需要 N7 登记**

### 3.2 新增：归因判定（Core，纯函数，可单测）

```swift
public enum Settlement {
    public struct Attribution: Sendable {
        public var candidate: CandidateID
        public var status: Status       // .attributable / .lost(Label)
    }
    public enum Status: Sendable, Equatable {
        case attributable
        case lost(Label)
    }
    public enum Label: String, Sendable, Equatable {
        case renamed, userDeleted, directoryRestructured, unattributable
    }

    /// 路径探针三态（可注入 ⇒ 归因判定是纯函数、可单测，不碰真文件系统）。
    public enum PathState: String, Sendable, Equatable {
        case exists        // 路径存在
        case absent        // 路径确定不存在
        case inaccessible  // 不可读（权限 / 跨 uid）—— 不判定
    }

    /// 逐条归因。`K` 由结果直接得出，`J = T − K` 派生。
    /// `probe` 对「条目路径」与「父目录路径」各探一次。
    public static func attribute(
        snapshot: [CandidateID],
        current: [CandidateID],
        probe: (String) -> PathState
    ) -> [Attribution]
}
```

**判据（必须按契约，不得自创）**：

| # | 情形 | 归因结果 |
|---|---|---|
| 1 | 身份键（`path + birthtime`）在 `current` 中 | `.attributable` |
| 2 | 路径**相同**但 `birthtime` 变化（**同名重建**） | `.lost(.directoryRestructured)` |
| 3 | 路径**不同**、同 `birthtime` 在 `current` 中**唯一**命中一条 | `.lost(.renamed)` |
| 4 | 路径**不同**、同 `birthtime` **命中不止一条**（匹配不唯一） | `.lost(.unattributable)` |
| 5 | `current` 中无同 `birthtime` 命中者，且该路径**不可读**（`lstat` 失败：权限 / 跨 uid） | `.lost(.unattributable)`（裁决 ③） |
| 6 | `current` 中无同 `birthtime` 命中者，且**父目录仍存在可读**、该路径**确定已不存在** | `.lost(.userDeleted)` |
| 7 | `current` 中无同 `birthtime` 命中者，且**父目录确定已不在**（父目录结构变化致路径失效）**或**该路径**仍在但已不再是候选** | `.lost(.directoryRestructured)` |
| 兜底 | `current` 中无同 `birthtime` 命中者，且**父目录不可读** | `.lost(.unattributable)` |

**判据按表序判定，首个命中者生效**（① → ② → ③ → ④ → ⑤ → ⑥ → ⑦ → 兜底）。

> **第 6 行 vs 第 7 行（原第 4/5 行）：必须靠**双探针**才分得开**（v4 更正）。
> v3 的「第 4 行 = 路径不存在 → 用户手删」「第 5 行 = 父目录结构变化 → 目录拆分合并」
> 在**只探条目路径**时不可执行：父目录被改名 / 被删与条目被删都表现为
> 「条目 `lstat` 失败」⇒ 两类**无法区分**，「目录拆分合并」将**永远判不出来**。
> v4 写死**探针三态**并**探两次**（条目路径 + 父目录路径）：
> **父目录确定已不在** ⇒ 目录结构变化（第 7 行）；
> **父目录仍存在可读**而**条目确定已不存在** ⇒ 条目被删（第 6 行）；
> **父目录不可读** ⇒ 不判定 ⇒ 兜底「无法归因」（不把未知判为安全，不变量③）。
> 探针**可注入** ⇒ 归因判定是纯函数、可单测。
>
> **第 3 行不得依赖 inode**（v3 更正）：初稿写「同 inode / birthtime 出现在新路径」，
> 但 PRD v5.5〔删 inode 判据〕已**删除** v4.0 的 inode 比对判据，明确
> 「改名检测**不得依赖 inode**」。
> 可行替代 = **同 `birthtime`、不同路径**（`birthtime` 在 `rename` 中不变）。
> 匹配必须**唯一**：同一 `birthtime` 命中多条 → 判据不成立 → 落第 7 行
> `.unattributable`（不把未知判为安全，不变量③）。

> **第 2 行的标签是契约指定的，不是我们挑的**：M3 算法行明写
> 「同名重建命中的条目**计入 `J`**（归因标签为「目录拆分合并」类之一）」。
> 初稿漏了这一行，会让同名重建落到第 7 行「无法归因」——与契约冲突。
>
> **第 2 行还决定了一件事**：重建后的**新条目转入下一轮快照**、不计入本轮样本。
> 所以本轮 `K` 不含它，下一轮 `T` 才会把它算进去。

### 3.3 新增：结算写入（AppModel）

在「观察期结束扫描」这一时刻：

1. 逐条归因 → `K`
2. `J = T − K`（派生，不独立算）
3. 写 `entry.K` / `entry.J` / `entry.snapshotDate` / `entry.settlementDate`
4. 写 `settlement.producedAt` / `reportId`
5. **同一次原子写入**落盘（不得分成两次 —— 否则会出现「`K` 非 nil 但
   `producedAt` nil」：界面显示未结算而门槛已在用 `K`）

**触发条件**（M1）：`countedDays == 14` 且本次扫描**成功且未中断** → 这次就是结算扫描。

> **「成功且未中断」的判定**：来源级失败（单个来源不可读）不阻断整体，
> 但**整体中断**（用户取消 / 超时 / 断电）**不算成功扫描** —— M1 明写
> 「成功扫描 = 扫描完成**且扫描本身成功**」，扫描引擎返回 `aborted`
> 即不是成功扫描。
>
> **取快照与结算互斥**：本轮**首次**成功 `full` 扫描取快照（写 `T` / `H` /
> `snapshotMembers`）；**观察期结束**的那次扫描做结算（写 `K` / `J`）。
> 同一轮里第一次成功扫描只取快照、**不结算**（当时观察期还没满）。

### 3.4 修复：`a` 的写入路径（**本单必做，不可推迟**）

`MissCounter` 已存在且有单测，但**生产零调用**。要接上：

1. 每次扫描后，用 L0 快照对每条候选做一次判定
2. `F` 置位（首检阴性）、`P_now` 求取、`C_done` 并入、`a` 累加
   —— 四者**同一次扫描内一次性完成**（M4「统一时点」）
3. 写 `entry.a`，并把 `F` / `C_done` / 位槽表写进 `SourcePayload`（**当前从不写入**）

**为什么不能推迟**：`a` 恒 0 会让门槛在「从未观测」的前提下成立 ——
那是伪造安全凭证（不变量④）。只修 `K` 不修 `a`，等于把产品从
「点不亮」改成「**不安全地点亮**」，比现状更糟。

**降级态的处理（M4 明写）**：同 uid 进程枚举失败（`degraded = true`）时，
该来源的 `a` / `b` **均不判定** → **不写 `0`、不覆盖**，保留上一轮的值；
界面第 ⑤ 页⑥填「无法判定（无法枚举本用户进程）」。
> ⚠️ 覆盖写 0 是**把未知当 0** —— 与不变量③直接冲突。
> 「无法判定」在数据层表现为**该来源本轮没有新的判定结果**。

**用户手删的例外（M4 明写）**：用户手动删除该候选致其无法复检 → **不计误判**。
判据里体现为：候选已不在本轮扫描结果中 → 不产生新的误判计数。

### 3.5 修复：`b` 改为累计（M5）

```swift
entry.b += bCount     // 本轮内累加；轮次切换时归零
```

`bCount` 是**该来源**本轮的候选判定次数（**不是**全局候选数——
原实现给每个来源都填了全局候选数，那是 §1.7 之外的又一个口径错误）。

### 3.6 修复：中断扫描不推进计数日（M1）

把 `advanceCountedDayIfNeeded` 移到「确认本次扫描成功且未中断」之后，
并**同时**修 §1.7-f（中断的 full 扫描不得用部分 candidates 取 `T`）。

**中止扫描仍然要落盘的部分**：`a` / `b` 的累计（**已实际执行的判定次数**如实计入）
与扫描日志。中止扫描**不**取快照、**不**结算、**不**推进计数日。

### 3.7 接线自检 + 单测

- 单测：归因七种情形各一例、`K + J = T` 恒等、同名重建不计入本轮、
  `pipx` 行不套恒等式、`a` 的逐候选判据（含 `C_done` 去重）、
  `b` 累计、中断不推进计数日
- 接线自检：真文件系统造快照 → 删几条 → 结算 → 断言 `K`/`J` 与预期一致；
  再断言 `a` / `b` / `producedAt` 非空且自洽

### 3.8 载体字段与语义修正（实现期发现，随本单一并改）

| 字段 | 现状 | 改为 | 理由 |
|---|---|---|---|
| `SourceHeaderEntry.slotCount` | 被 `persist()` 写成「本次扫描的候选数」 | **位槽数**（`SlotTable.slotDomainSize`） | 载体解码时用它断言位图长度 `= ceil(slotCount/8)`（M4「位槽号稠密递增、从 0 开始、永不回收」）。原语义下这个不变量在写入真实位图后**必然不成立**。`T` 与位槽数就此**解耦** |

| `SourceHeaderEntry.settlementDate` | 无 | 新增 | 结算时刻 |
| `SourceHeaderEntry.unattributableCount` | 无 | 新增 | 「有 N 条无法归因」（裁决 ③） |
| `settlement.producedAt` | 版本变更时**不清零** | 版本变更时**一并清零** | M1 版本变更终值 ③「`K`/`J` 清零」——`producedAt` 是结算凭证，与 `K`/`J` 同组。不清零 → 界面在观察期重启后仍显示「已结算」 |
| `autoDeleteEnabled` | 版本变更时被**静默置 `false`** | **保留** | 用户设置不是凭证（§五② 记的既有缺陷） |

## 五、裁决结果（v3 · 2026-11-16 · 已全部裁决，进入实现）

### ① 快照清单的存储位置 —— **裁决：接受载体变大（选项 C）**

> **背景**：R2 v1.8 `:733` 已把「位槽表体量（3M 候选 ≈ 336 MB）与 M4 的
> 「约 1 MB 量级」不一致」登记为 **PM 裁决项 D-03**。
> 也就是说：**载体规模冲突在契约内部早已存在且已登记**，与本单无关。
> 本单要裁决的只有一件事：**快照成员集合放在哪**。

**裁决结果**：快照成员集合作为 **`state.residue` 每来源的第 4 个段**
（`SegmentKind.snapshot = 0x04`），**接受载体变大**，并据此修订
M4「载体规模口径」（PRD v5.6）。

| 选项 | 做法 | 裁决 |
|---|---|---|
| A | 快照成员集合落 `state/snapshot-<round>.json`，不进 `state.residue` | ✗ 未采用 |
| B | 复用位槽表 + 快照轮次戳 | ✗ 未采用（位槽号只增不回收，「槽号 ≤ N」无法区分「快照时已存在」与「快照后才分配」） |
| **C** | **接受载体变大，修订 M4 口径** | ✅ **采用** |

**理由**：

1. **不引入新的载体机制** —— 快照成员集合与 `a` 的载体四项本就在同一个
   文件里、同一套原子写与 CRC32 保护之下；拆成第二个文件就多一次
   「写了一半」的中间态，而 `K` 的分母必须与 `T` **同源**（同一个 `save()`）。
2. **不引入新的 N7 义务** —— `state.residue` 本来就**不属 N7 的 `.jsonl`
   记录目录**、不计入 N7 计量、「一键清除」不作用于它；快照清单含候选路径
   **不引入新的隐私类**，**不需要 N7 登记**。
   （选项 A 反倒要第二张单把它登记进 N7 清除范围。）
3. **规模冲突本就在契约里**（D-03）—— 既然已被登记且本单必须给出
   一个自洽的落点，**正面修订口径**比绕开它更诚实。

**连带修订**：M4「载体规模口径只有一处」的那一句「约 1 MB 量级」必须改
——**代码与文档对不上就是缺陷**。修订写进 PRD v5.6 的变更清单，
**旧的「约 1 MB 量级」句作废登记**（保留作废痕迹，不静默改写历史）。

### ② 旧载体的迁移 —— **裁决：接受重置（就地升级）**

**裁决结果**：schema 1 → 2 **就地升级**；旧载体升级后，
**首次成功扫描重新取快照，观察期从头开始**。

- 不走 `E-301` 只读降级 —— 否则老用户升级后**整个观察期作废**且
  应用进只读态，比「重来一轮」更糟
- 「升级即重置观察期」与既有规则「应用版本变更重置观察期」
  （M1 版本变更终值）**一致**，不是新语义

**同时必须修的既有缺陷**（原 §五② 记的）：

> `clearCarrierForVersionChange` 造的是**全新 `StateHeader()`**，
> 只把 `appVersion` / `round` 填回去 —— 于是 `autoDeleteEnabled` 被
> **静默置 `false`**、`sources` 被清空。
>
> 后果：用户升级一次，**已经点亮的自动删除开关被悄悄关掉**，而界面不会
> 提示原因。这不是「重置观察期」，是「丢失用户设置」。
>
> **裁决一并要求**：迁移实现必须改成「保留 `autoDeleteEnabled` 等用户设置，
> 只清凭证类字段」（`F` / `C_done` / 位槽占用表 / `a` / `K` / `J` /
> `settlement.producedAt`）。

### ③ 归因需要读文件系统，与「不把未知判为安全」

**裁决结果**：判 **`.lost(.unattributable)`**，并在界面如实标注
「有 N 条无法归因」。

- 判 `.attributable` → **把未知判为安全**（违反不变量③）
- 判 `.lost` → `K` 偏小 → 门槛偏严（保守，但可能让用户永远点不亮）
- 保守方向正确（宁可点不亮，不可误判可删），但要在 UI 上说清「有 N 条无法归因」

**落地**：`SourceHeaderEntry.unattributableCount` 承载该数，
导出报告如实呈现（**不隐藏**）。

### ④ §三新增项 —— **裁决：一并纳入本单**

`a` 写入路径、`b` 累计、中止扫描不推进计数日 —— 三处随本单一起修。
理由见 §七②：**不修就不能算完成**。

### 8.1 缺陷 1 详述：`birthtime` 往返非无损（本单最危险的一处）

**现象**：写「快照成员集合落盘」时发现，`birthtime` 用 `f64` 存，而
`Date` 的内部表示是「相对 **2001-01-01** 的秒」（一个 `Double`），
`timeIntervalSince1970` 与它之间隔着 **978307200 秒** ⇒ 两者落在**不同的
f64 网格**上（当前量级：内部值刻度 2⁻²³ 秒、Unix 值刻度 2⁻²² 秒）⇒
**用 Unix 基准编码、用内部基准解读，往返必然丢 1 位**（1 ULP ≈ 1.19e-7 秒）。

**为什么这是 P0**：丢位破坏的不是「精度」，而是**身份键**——而身份键是
`K` 与 `a` 两条判据**共同的**输入：

1. **归因判据失灵**：「路径 + birthtime 命中」不命中 ⇒ 同路径但 birthtime 不同
   ⇒ 判「同名重建」⇒ `K = 0`、`J = T` ⇒ 一份**全是假失联**的报告；
2. **位槽占用表的身份键被破坏** ⇒ 每轮扫描都重新分配位槽 ⇒ **`F` 位永不命中**
   ⇒ `a` 恒为 0 ⇒ 门槛项读数恒 0，**等于没有这条门槛**。

**处置**：`ResidueStateFile.BirthtimeBase` 按 `schemaVersion` 选基准
（schema 1 = **Unix 纪元**，存量文件语义不变；schema 2 = **参考纪元**，
位模式往返 100% 无损）；**读方不得猜测基准**。
规格补进 R2 v1.9 §5.1.1「`birthtime f64` 的记录基准」。

> **教训**：「两个值相等」不等于「它们同义」——**同一个物理量在不同基准下的
> 数值不相等**，而这里的基准差异藏在**表示层**里，肉眼读代码看不出来。

### 8.2 缺陷 3 详述：守门脚本自己变弱（比被守的东西出错更隐蔽）

**现象**：§3.6 把计数日推进搬进 Core（`ObservationWriteback.swift`）之后，
`verify_a9.sh` 里那条「M1 计数日推进」检查项**不再指向任何真实调用点**——
它grep 不到东西时不报错，只是**空过**。

**为什么危险**：这是「**守卫失效**」而不是「被守卫的代码出错」。被守卫的代码
就算退回旧写法（编排层自己 `countedDays += 1`），这条检查**也不会红**。
一条永远绿的检查比没有检查更坏——它让人以为有网。

**处置**：改写为**更强**的形式：① 推进逻辑的**实现**必须在 Core；
② **调用点**也必须在 Core（编排层出现 `advanceCountedDay` / `countedDays +=`
即判不通过）。旧写法「只查编排层」作废。

### 8.4 缺陷 6 详述：`fSetBits` 取证字段**本单之前碰巧正确、本单之后开始撒谎**（v6 已修）

**现象**：导出报告的取证段渲染 `| fSetBits | N |`（`Redactor.swift:338`），
而这个 `N` 的来源 `AppModel.swift:733` 是**字面量 `0`**：

```
lastScanDiagnostics = ScanLogRecord.Diagnostics(
    …
    fSetBits: 0,          // ← 写死
```

Core 侧 `NegativeBitmap`（`Metrics.swift:185`）只有 `capacityBits` / `byteSize` /
`isSet` / `set` / `clearAll` / `dataRepresentation` / `init(data:bitCount:)` ——
**没有任何「数置位数」的 API**（全仓 `setBitCount|popcount|countSetBits` 零命中）。

**为什么是「本单之后」才开始撒谎**：`F` 位图（`SourceL0State.negativeSeen`）的
唯一写入点是 `Metrics.swift:384` 的 `negativeSeen.set(slot)`，它由
`MissCounter.apply` 触发。而 **`MissCounter.apply` 在 CR-031 之前全仓无调用点**
（`git grep MissCounter.apply HEAD` 零命中）⇒ 位图**恒空** ⇒ `fSetBits: 0`
**碰巧等于真值**。本单新增 `ObservationWriteback.swift:151` 这个唯一调用点后，
位图**第一次真的会被置位**，而诊断字段仍写死 `0` ⇒
**从「碰巧对」变成「稳定的错」**。

**为什么没有任何测试能发现**：`RedactorTests.swift:55` 的 `fSetBits: 30`、
`UpstreamAndRecordTests.swift:189` 的 `fSetBits: 90` 都是**测试自造值**——
测的是「字段有没有被透传」，**不是「这个数字算得对不对」**。
没有一条测试从**真实位图**推出期望值 ⇒ 把 `0` 换成 `999` 测试照样绿。
这与 §8.2 是同一类问题的另一面：**§8.2 是守卫失效，这里是守卫根本不存在**。

**影响面（界定清楚，避免夸大）**：`fSetBits` 是**取证/诊断字段**，
**不参与门槛判定**（门槛只读 `K` / `T` / `a` / `b` / `producedAt`）⇒
**不影响本单验收判据 1–20**。但它是**用户可读的取证材料**，写死 `0` 违反
不变量③「不把未知判为安全」的同类要求 —— 这里是把「没算」写成了「算是 0」。

**为什么本单不修**：不在验收判据内，且修它要动 Core 的**公共 API 面**
（新增 `NegativeBitmap.setBitCount`）⇒ 属独立改动，不宜夹带。

#### v6 的处置（**照上面「另开单时怎么做」的四步原样执行**）

1. **RED 单测**（TDD 铁律）：`MetricsTests.swift:332`
   `testBitmapSetBitCountCountsEverySetBit` —— 空位图 ⇒ `0`；
   置位 `[0, 5, 63, 64, 127, 128]`（**跨 64 位字边界**）⇒ `6`。
   `ObservationWritebackTests.swift:546`
   `testPayloadSetBitCountEqualsNegativeVerdictCount` —— 4 条候选里
   2 条判「无活引用」⇒ 载荷的 `fSetBitCount == 2`（其余两条：
   「有活引用」不置位、「判不出」**不置位** —— 不变量③）。
   **RED 实测**：诊断 `0` / 载体 `2`（**正是缺陷本身的样子**）。
2. **Core 加 API**：`Metrics.swift:254`
   `NegativeBitmap.setBitCount(ofBytes:)` —— 纯函数，逐字节 `nonzeroBitCount`，
   **无 IO**。数的是**字节表示**（`SourcePayload.bitmap` 的载体形态），
   因为取证字段的口径必须是**盘上的那串字节**；两种表示互为无损映射
   （补齐位恒为 0），数出来必然相同。
3. **`AppModel` 从载体取数**：`AppModel.swift:733` 改为
   `contents.payloads.values.reduce(0) { $0 + $1.fSetBitCount }`
   （`ResidueStateFile.swift:180` 的委托方法）—— **不另算一份**（不变量②）；
   与 `doneCount` 同一口径（同样从载体读）。
4. **夹具改由真实位图推导**：`RedactorTests.swift` 与
   `UpstreamAndRecordTests.swift` 各加私有方法 `realFSetBits(setSlots:)`，
   造**真实 `NegativeBitmap`** 后调 `NegativeBitmap.setBitCount(ofBytes:)` ——
   夹具与生产**共用同一原语**，口径一旦漂移夹具立刻显形。

**另加一道守卫（`AppModel` 侧无单测，只能靠接线自检）**：
`WiringSelfCheck.swift:199` 新增一项 —— 首轮扫描后读回载体，
断言 `诊断 fSetBits == 载体置位数`，**且** `载体置位数 == 2`（**钉住绝对值**）。
**为什么不能只断言「两边相等」**：载体为 0 位时 `0 == 0` **假绿** ——
而那**正是缺陷本身的样子**（诊断 0 / 载体 0）。必须钉住绝对值才拦得住。
**GREEN 实测**：`诊断 2 / 载体 2`；接线自检 78 → **79 项**。
