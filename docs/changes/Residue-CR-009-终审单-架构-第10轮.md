### 五处点名推演（逐条亲手推）

**① 量的唯一性 —— 团队点名的三个具体追问**

- **`a` 的判据前置「影子期内做 L0 判定」在契约层是否真被要求？** **要求存在，但落点只在指标定义表本身。** 全文**无任何 AC 的 Then/判定要求产品在观察期内执行 L0 判定**（AC-05 / AC-17 的 L0 均在删除链路上；AC-01 只读扫描的 Then 只要求三区块报告；AC-09 Then 只要求「记录『后续是否被重新用到』」）。M4 判据行以「**前置（影子期必须做 L0 判定）**」的形式把它写进契约，且 M5 的「`b = 0` 只可能出现在『该来源在判定域内但从未被扫描过』」与之同向 → **契约层自洽、可执行；验收层只能验到 `b ≥ 1` 这一下限，无法验「每扫描每候选各一次」**（建议 #5）。
- **执行它会不会违反 AC-09「报告只含建议、不执行任何删除」或 N2「影子观察期不属本节信号采集，不受关闭自动删除后采集全停影响」？** **都不违反。** L0 判定是**只读判定**（P-L0「持有」判据 = 枚举 fd / 锁 / cwd），既非删除、也非「四档信号采集」（四档 = L2 弱感知层，AC-10 / AC-11 / N2 语境），AC-09 Then 的「不执行任何删除」只约束动作、不约束判定；N2 的豁免句只说影子期观测机制不属本节信号采集。**M4 的前置与 AC-09 / N2 均不冲突。**
- **「首次检查时刻」子值被两个用途复用会不会冲突？** **会，且比预想更宽——是三用。** M4 写入时刻把**复检时刻**写进「首次检查时刻」子值；M6 把该子值取作**记录时刻**（留存年龄起点）；P-L0 / AC-17 把它定义为 **L0 检查窗口的起点**（删除链路语义）。三用本身不必然冲突（若「复检」= 新增一行，则该行子值 = 该行写入时刻 = 记录时刻，三者同值）；**但 M4 未规定「复检 = 新增一行」还是「更新原行」**，两种读法给出三个不同的后果（举证链行数、`a` 判据可执行性、90 天期限是否对举证链行生效）→ **阻塞 #4**。

**② 写入口与终值：应用版本变更 / 开轮 / 结束扫描三者同刻发生时，七个量是否都有唯一终值？**

- **应用版本变更**：计数日（归零）、轮次（不变）、`a`（清零）**有唯一值**；**`T` / `K` / `J` / `b` 无唯一值**（`T` 两读、`K`/`J`/`b` 无规则）→ 阻塞 #2。
- **自动开轮**：计数日（归零）、轮次（+1）、`a`（保留）、`T`（**不在开轮时取**，改由新一轮首次成功扫描取 —— A8 已闭合）、`K`/`J`（旧轮已冻结）→ **有唯一值**。
- **结束扫描**：`K`（冻结）、`J`（派生）、`T`（不变）→ 有唯一值；`b` 即时写、`a` 在报告产出后判定 → 有唯一值。
- **三者同刻**：文件头② 已给优先级（「先结算本轮、后执行应用版本重置」，`a` 终值 = 0）→ `a` 唯一；其余量同 #2。**结论：七量中三个（`T` / `K` / `J` / `b` 中的四个）在版本变更这一写入口上无唯一终值。**

**③ 非循环：`K` 与 `J` 是否仍是循环关系？自己代数推一遍。**

- 按 M3 唯一式：快照逐条归因直出 `K`（例：`T = 30`，归因得 `K = 28`）→ `J = T − K = 2` → `K + J = 30` ✔。
- 按 AC-09 ③ 的字面：`K + J = T`（**恒等式，不是 ≤**）——因 `J` 被**定义为** `T − K`，该断言在构造上**恒真、不可证伪**（实现方若让 ③ 单元格里显示的 `J` ≠ `T − K`，则 ③ 失败 → 仍有对**显示层**的判别力；但对**归因层**无判别力：无论归因逻辑多离谱，`J` 派生都使等式成立）。
- 全文已无第二条能给出不同 `J` 的路径（组 B 的 `K = T − J` 已删、AC-08 组 B 判定已改为引用 M3、AC-09 Then 已改为「先算 `K` 再派生 `J`、不得由 `J` 反推 `K`」）→ **无循环**。
- **结论：非循环成立。** 唯一残留是「AC-09 ③ 对归因层不可证伪」这一点 —— 但 M3 明确「`J` 为派生量」并已把可证伪性交给「逐条归因结果 + 失联四类归因标签」承载 → **不判阻塞**，登记为建议 #6（说明 ③ 的判别力边界）。

**④ 边界：M1 改「日历日计数」后，观察期实际时长与 S2 / AC-08 组 B 是否一致？**

- 计数日 = 有成功扫描的**日历日**数，一天最多 +1，且「该次成功扫描记为第 1 日」→ 14 个计数日 **必然跨 ≥ 14 个不同日历日**（首个计数日 = 本轮首次成功扫描日）→ **观察期实际时长 ≥ 14 个日历日**，与 S2「每轮观察期 14 天」、V1「影子观察期 14 天」、AC-08 组 B「本轮计数日 ≥ 14」**一致**。上轮阻塞 #6 关闭。
- 边界值说明：「观察期结束扫描 = 本轮第 14 个计数日**结束后的第一次成功扫描**」→ 该扫描自身落在第 15 个成功扫描日 → 观察期**实际为 15 个成功扫描日**（≥ 14，仍满足承诺方向）→ 不判阻塞，登记建议 #7（说明口径为「≥ 14」）。
- **N3「默认每日 1 次」与计数日的相容性**：定时任务每日 1 次 ⇒ 14 计数日 ≈ 14 日历日，无冲突。

**⑤ 死局检查：计数日只增不减、失败日不计、不设超时上限 —— 是否仍可能永远点不亮？**

- **路径 1（已如实登记）**：扫描长期失败 / 用户长期不开机 → 计数日不再增 → 观察期永不结束 → 永不点亮。文件头① 已写「**不设超时上限**（如实登记：扫描一直失败则永远不点亮，因为无法完成结算）」并给出唯一样式串「第 `<N>` 轮 · 观察期未满 · 待结算扫描（无需操作）」+ 剩余天数显示 `—` → **属已登记边界，不判阻塞**（上轮同判）。
- **路径 2（上轮之后新出现）**：**统计「已观察天数」改为「日历日数」后，死局的成因从「失败日不计」扩展为「扫描频率低于每日一次」**——但 M1 的定义是「有成功扫描的日历日数」，只要**每个日历日**至多 +1 且失败日不计，则**需要 14 个不同的日历日各至少一次成功扫描**；用户在 14 天内每天都开机并扫描一次即可走满 → 死局仅由「持续不扫描」造成，已登记。
